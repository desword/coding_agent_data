# 多 Coding Agent 开发的 10 个具体项目

检索时间：2026-11-16。依据：[场景检索与评估依据](场景检索与评估依据.md)。本清单的对象是**正在开发或已经开发出的具体软件**，不是单纯的 Agent 框架。所有链接固定到本轮查阅的仓库版本；项目作者的公开说明和记录不等于独立复核或完整网络实测。

## 先说明证据边界

- 下表的应用都有公开代码或明确的可运行开发项目，文档将其开发过程与 Codex 或 Claude Code 的多个角色/Agent 联系起来。但公开证据的强弱不一：有些提供多轮记录，有些主要是作者描述与角色配置。
- **没有发现可以证明这 10 个项目全部满足每个硬条件的证据**：特别是实际并发规模、是否所有通信经过 Leader、Topic 的原生实现、真实跨服务器数据量和网络瓶颈。缺失的项目标为“待验证”，不能用压力测试假设补成既成事实。
- 真正的 Agent 协作事件、应用运行时业务流量、构建与模型调用要分开统计。可以依据公开的工作流设计 Topic 和跨服务器适配，但适配属于我们的实验，不是原项目的公开实现。
- Aurora 与 Omakase 是同一作者、相似教学形式的两个具体商店项目，**不是两个独立验证来源**。尽管各有代码库，本清单标明这一依赖关系，不用它们证明两个独立团队有相同实践。

## 1. 本地账单与支出分析（Codex）

- **应用**：[expense-app-loop-built](https://github.com/hanco1/expense-app-loop-built/tree/62ec296b49fa17aac73fb8feb9261dcf79b5fda3) 是本地支出分析 Web 应用，提供账单导入、分类、月度统计和图表。项目以合成数据验证，不需要真实财务数据。
- **公开开发事实**：[README](https://github.com/hanco1/expense-app-loop-built/blob/62ec296b49fa17aac73fb8feb9261dcf79b5fda3/README.md)称使用 `codex-agent-loop-orchestrator` 和四个 AI lane：product 分解并派发、data-eng 做后端、frontend 做界面、review 审查；公开了请求、结果、返工与人工验收记录。[角色定义](https://github.com/hanco1/expense-app-loop-built/blob/62ec296b49fa17aac73fb8feb9261dcf79b5fda3/docs/loop/agent-lanes.md) 与 [运行日志](https://github.com/hanco1/expense-app-loop-built/blob/62ec296b49fa17aac73fb8feb9261dcf79b5fda3/docs/loop/loop-run-log.md)可以核对。
- **相关任务**：例如月度支出图表经历实现、审查、修复、人工发现显示问题、再次测试修复。请求和反馈与应用功能直接关联，并非人为填充消息。
- **待验证/扩展**：记录含 product 与 Worker 之间的交互，也含 Worker 与 review 之间的交互；不能说全都经 Leader 中继。是否同时运行、真实网络发送次数/大小及延迟未知。为研究 Topic 或交换机需另外实现适配并保留原生基线。

## 2. 全栈健身追踪

- **应用与证据**：[Fitness App README](https://github.com/kumaran-is/claude-agent-teams-demo-app/blob/8b56a175bb6fe63bcec6ae89d1ac0125a08f531f/README.md)描述运动记录、营养和目标管理，使用 Flutter、Spring Boot 和 PostgreSQL。作者称使用 Claude Code Agent Teams 编排七个专门 Agent，处理并行工作、共享契约和依赖门禁；[项目配置](https://github.com/kumaran-is/claude-agent-teams-demo-app/blob/8b56a175bb6fe63bcec6ae89d1ac0125a08f531f/CLAUDE.md)给出任务管理及角色/技术栈。
- **关联与限制**：前后端契约、测试和安全审查有协作理由；作者说明主要是项目演示，不等同于独立验证的生产负载。文档提供浏览器演示模式，不能因为有 Flutter/Android 就断定每个 Worker 必须使用模拟器。7 个 Agent 的通信轨迹与 Leader 中继程度待核实。

## 3. Factory4X 实时策略与工厂游戏

- **应用与证据**：[项目说明](https://github.com/tQuarella/factory4x/blob/b3f40f31935830ea5d7eec036c606a3ced924c1d/CLAUDE.md)称这是 Claude Code Agent 团队构建的实时策略/工厂游戏，主会话作为 Director。[开发流程](https://github.com/tQuarella/factory4x/blob/b3f40f31935830ea5d7eec036c606a3ced924c1d/PROCESS.md)描述 Director 分工、最多 3 名工程师并行、独立 worktree、Critic 审查、Director 合并，以及任务间依赖。[状态账本](https://github.com/tQuarella/factory4x/blob/b3f40f31935830ea5d7eec036c606a3ced924c1d/STATUS.md)记录实际迭代、审批、拒绝和恢复任务。
- **关联与限制**：任务依赖和审查汇合非常适合验证第二、三项功能。实际文件状态更新不自动等于网络消息；Lead 的实际包速率及压力未知。文档的并发上限是该项目自身流程配置，不是框架最大容量。

## 4. 浏览器塔防游戏

- **应用与证据**：[README](https://github.com/kodkod88/tower-defense/blob/e91893a618ec5a63afddef2c0561214cddf4d721/README.md)描述由 Claude Code Agent Team 构建的 TypeScript/Vite 塔防游戏。[团队契约](https://github.com/kodkod88/tower-defense/blob/e91893a618ec5a63afddef2c0561214cddf4d721/CLAUDE.md)列明 Lead、核心架构、玩法、渲染、内容和 QA 分工；[Backlog](https://github.com/kodkod88/tower-defense/blob/e91893a618ec5a63afddef2c0561214cddf4d721/docs/BACKLOG.md)记录具体任务和前驱依赖。
- **关联与限制**：核心类型、玩法、渲染和 QA 之间有明确依赖，适合测任务触发。文档要求需要跨文件修改时可直接联系对应队友，因此原始模式并非“所有消息经过 Leader”；Topic 或集中转发是对照实验扩展。

## 5. 游戏机维修店管理

- **应用与证据**：[Console Repair Shop Manager](https://github.com/Seb-programer/console-repair-shop/blob/dfb732b5ab38cfc902b28ebf57158f5ddef3481f/README.md)是维修、销售及客户查询全栈应用。作者描述使用 Claude Code 及 orchestrator、数据库、后端、前端、QA 角色；[项目案例](https://github.com/Seb-programer/console-repair-shop/blob/dfb732b5ab38cfc902b28ebf57158f5ddef3481f/docs/case-study.md)描述数据库、前后端按共享契约并行，交换注意事项，然后由协调者和 QA 验证。
- **关联与限制**：有真实业务模块、接口契约和反馈修复；作者本人同时承担产品和审查决策，不能把所有判断归给 Agent。公开说明不包含完整消息传递轨迹或实测流量。

## 对案例 1 的公开记录做的初步统计

针对固定版本 `62ec296b49fa17aac73fb8feb9261dcf79b5fda3`，读取 `docs/loop/messages/` 内全部 Markdown 文件，按文件中 `from_lane`、`to_lane` 和 `message_type` 统计：

| 指标 | 结果 | 边界 |
|---|---:|---|
| 消息记录文件 | 89 份 | 是仓库中保留的文件，不保证包含所有实际消息 |
| 文件总大小 | 320,705 字节 | 文件 UTF-8 字节，包含字段、标题和正文，不是网络流量 |
| 文件大小中位数 / 最大值 | 3,349 / 7,901 字节 | 仅对这 89 个文件计算 |
| product 与其他 Agent 相互往来 | 64 份 | 按文件的角色字段分类 |
| 非 product 的 Agent 互相往来 | 23 份 | 例如 data-eng 与 review；不证明真实传输路径 |
| product 发往 human | 2 份 | 单独列出，不算 Agent–Agent |
| 标注的时间跨度 | 2026-07-12 20:04:17 UTC 至 2026-07-15 23:17:42 UTC | 是记录中的 `created_at`，不是网络收发时间 |

类型包括 20 份 `REVIEW_REQUEST`、17 份 `IMPLEMENTATION_DONE`、17 份 `LOOP_STATUS`、12 份 `FIX_REQUEST`，其余为实现请求、审查结果、阻塞和人工验收等。文件字段和汇总不能证明每份都经网络发送一次，也无法推算数据包、送达延迟或整个运行期间的并发数。记录的时间间隔包含 Agent 工作和人工等待。

## 本轮实际复现和后续测试

我在 Linux 检出案例 1 的上述固定版本：后端 `unittest` **68 项通过**；启动其本地服务后，主页返回 **HTTP 200**。这是应用基线验证，不是重新运行四个 Codex Agent，也不是通信测试。仓库中的历史消息统计与本次应用基线分别得到，不能混为一次新实验。

优先顺序建议：先用案例 1 作为 **Codex 真实公开记录基线**；再用案例 3 或 4 比较明确依赖关系和并行开发；案例 2 作为有移动端和后端的扩展。下一步需要为选定应用固定可复现的原始任务、构建真正的一键 Agent 测试和消息观测，记录自然运行后再做 Topic/跨服务器及压力对照。目前还没有完成该一键真实 Coding 测试或测出网络瓶颈。
