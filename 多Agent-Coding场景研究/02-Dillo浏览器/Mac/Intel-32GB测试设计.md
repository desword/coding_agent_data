# 单台 Intel 32 GB Mac 的多 Agent 测试设计

本方案对应 [Dillo 一键实验](../README.md)。目标是获取一次真实开发中的 Agent 资源占用、实际经过实验中继的协作消息、同机处理和等待时间，再根据观测轨迹推演数据中心 10 Gbps 单向链路。固定任务、固定版本和工作分工见项目说明。模型在远端运行；Mac 上测到的是本机 CLI、工具和中继，远端模型的 CPU、内存与 GPU 不在测量范围。

## 1. 建议配置与实验顺序

| 项目 | 首次运行配置 | 理由与口径 |
|---|---|---|
| 项目与角色 | Dillo 固定版本；1 Leader + 5 Worker | 目前脚本固定五个角色，Leader 决定启动时机；不要求所有 Worker 始终处于活跃状态。不要把五个进程存在等同五次同时推理。 |
| 运行数量 | 一次只运行一个实验批次 | 避免多个批次相互干扰和抢占本机 CPU、内存、编译资源及模型配额。 |
| 任务 | 现有 UTF-8 下载文件名开发、测试、安全检查、集成与审查 | 采用同一个真实任务比较多次运行；不人为填充通信内容。 |
| 资源采样 | Agent 进程树 CPU 与 RSS 约 1 秒；macOS `vm_stat` 和 `vm.swapusage` 约 5 秒 | 保留逐时刻数据；macOS 没有准确获得时留空，不把空值记为零。 |
| 准备基线 | 正式开始前记录一次主机内存快照；正常使用的后台软件尽量保持一致 | 快照在正式计时之外。当前版本还没有自动连续采样 30 秒空闲基线。 |
| 正式计时 | Leader 开始至开发与最终独立验证结束；报告另列 Leader 开发与独立验证 | 代码下载、登录、模型预检、准备和基线测试不计入。 |
| 重复 | 首先完成 1 次并检查证据；再按相同配置至少运行 3 次，用独立批次保存 | 模型输出、调度和调用时间有波动。三次可以观察变动，不能把少量消息的 P99 当成稳定结果。 |
| 外部条件 | 接电源、保持散热、避免睡眠，记录 macOS、CPU 核数、内存、Codex 版本与可识别的模型信息 | 不需要安装模拟器或为 Agent 新建虚拟机。当前脚本不自动检测电源、热降频或具体模型版本；遇到时人工记录。 |

32 GB 是物理内存总量，不等于本实验可独占的内存。Intel Mac 的实际核心数、其他应用及网络状态各不相同，因此不预先宣称 5 个 Worker 一定不会受到资源约束。实际观察 Leader、W1–W5 和系统内存：如果 CPU 长时间高占用、系统持续发生明显换页、其他应用明显卡顿，则把该批次标注为本机资源竞争，并关闭其他重负载后重跑。已有批次保留，不把资源竞争时的数据当成无干扰基线。

当前脚本固定五个 Worker，**没有 2、3、4 Worker 并发上限配置，也不会自动按内存压力限流**。需要更低并发时，应修改 Leader 派工与启动顺序，将五个角色分批执行，并保留同样的任务和验收；不能只限制进程数而让现有 Leader 一直等待尚未启动的角色。不同并发档位属于不同实验条件。先获得完整五角色基线后，再决定是否实现分批对照。

## 2. CPU、内存和开发时延

1. 脚本记录 `记录/每Agent资源.csv`：逐角色的进程树 PID 数、RSS 和 CPU，包含其仍存活的构建与工具子进程。CPU 的 **100% 表示占满一个逻辑 CPU**；多线程可以超过 100%。用每秒数据看平均、峰值和持续时间，同时与本机逻辑 CPU 数比较。Agent 进程存续期间的平均值包含等待，不等于忙碌时平均值。
2. RSS 是进程驻留内存估计；共享页可能被多个进程重复计算，进程树 RSS 相加不是整机唯一物理占用。采样可能漏掉短时子进程，或者遗漏独立守护进程；远端模型和其他用户应用不归属于某个 Worker。
3. `记录/系统内存采样.csv` 保存 macOS 原始 `vm_stat` 与 `vm.swapusage`。对照 `实验状态.json` 里的准备结束快照，检查测试期间 swap 使用和 `Swapouts` 等累计计数是否持续增长；累计值本身大不证明当前实验正在换页。文件缓存可以回收，不能简单把 `Pages free` 当成可用内存。当前脚本不自动判断 macOS Memory Pressure 等级，可同时人工查看“活动监视器 → 内存”中的内存压力曲线。
4. 区分 Leader 开发、Worker 生命周期、工具执行、Git 集成、独立验证、路由和排队。它们可能并发、重叠，不能求和得到总耗时。模型推理时延只有 Codex/服务端明确导出的计时才计入，未提供则标记不可得；本机进程生命周期、请求等待和工具耗时不代替模型推理时间。
5. `router` 同时包含协调、采样、脚本及脚本发起的工作；它的 CPU 不是纯路由 CPU，也不能直接换算成数据中心某台服务器的包处理能力。需在目标服务器用同协议、同负载单独测量。

Mac 上 `ps` 一秒采样得到的是近似值，可能错过短命编译进程。当前首次观察到一个进程时，会把其已累计的 CPU 时间归入当次采样，可能抬高该秒峰值；因此短时峰值用于发现可疑区间，不作为精确的单秒 CPU 用量。要精确测短工具及 CPU 总量，应后续增加进程退出时资源统计并做采样开销对照。

## 3. 消息数据量与同机延迟

`记录/消息明细.csv` 保留消息内容、发送方、接收方、Topic、正文 UTF-8 大小及投递确认状态。`记录/每秒通信速率.csv` 新增两个方向的**入队正文**字节和消息副本数：

- Worker → Leader：Worker 发给 Leader 的一份正文。
- Leader → Worker：Lead 逐接收者投递的正文；一条消息发给 4 个订阅者则计算 4 份。订阅变化见 `记录/订阅事件.csv`。
- 入队量是准备交付的负载，包含最终未领取的消息；消息明细和报告还单独给出已确认领取的副本。排查丢失或失败时，两者不能混为一谈。

按正式任务全周期计算方向平均速率；每秒固定窗口观察突发，最后一个不足 1 秒的窗口仍按 1 秒显示。单条消息跨窗口边界或多个事件集中在窗口边界时，固定单秒峰值可能低估任意滑动 1 秒峰值。JSON 请求和响应正文另行记录；它们含轮询、确认等操作，不与消息正文重复相加计算同一方向的应用数据。

路由是实验自行实现的本机 HTTP Topic 中继，并非 Codex 原生多 Agent 通信。进程初始提示、模型 API 调用、共享文件、Git、绕开此中继的通信没有包含在上述正文中；上报的是本实验中继可观察到的流量。

本机单调时钟可配对以下阶段，保留每阶段样本数：

| 阶段 | 主要含义 |
|---|---|
| 客户端发送 → 服务接收 | 本机 IPC、HTTP 解析和调度的一部分；不包含客户端脚本进程启动时间。 |
| 服务接收 → 逐接收者入队 | 服务路由和入队；不包含接收请求之前的整个服务处理。 |
| 入队 → 接收方轮询领取 | 队列等待，包含 Agent 正在推理、执行工具或尚未轮询的时间。 |
| 出队 → 客户端收到 | 响应、本机 IPC、解析和调度。 |
| 客户端发送 → 客户端收到 | 本机完整可配对投递区间，包含队列等待；客户端确认收到不证明模型已阅读。 |

按消息类型和方向分别查看样本数、中位数及最大值。当前报告至少有 20 个样本才给 P95、至少 100 个才给 P99；这些最低数量仅避免极端小样本，统计仍可能不稳定。**不能将这些本机时间直接称为跨服务器网络延迟**，也不能将 Agent 排队等待归因于交换机。

## 4. 从本机轨迹推演 10 Gbps

假定 Leader 与中继放在一台服务器、所有 Worker 位于另一侧，并假定消息都要经过这条链路。逐条使用真实 `enqueue` 时间、正文大小、方向和实际接收人数构造输入事件；本机该两方向的入队量就是此拓扑下的**应用正文需求**，不是实际网卡流量。若 Worker 与 Leader 同机、Worker 分布在多个网络出口，或多台机器本地聚合，跨目标链路的副本数需要按具体放置重新计算。

单方向上，在时间窗 T 内的正文速率为 `8 × 该方向正文副本字节 / T`，单位 bit/s；单方向正文占比为该速率除以 `10,000,000,000 bit/s`。例如，100 秒内向 Worker 入队 100 MiB 正文副本，平均正文速率约 **8.39 Mbps**，约为 10 Gbps 的 **0.084%**。这是说明计算方法的假设例子。反方向单独计算；不能把全双工两个方向相加再与单向 10 Gbps 比较。JSON、HTTP、TCP/IP、链路帧、ACK、重传及加密等会增加真实链路负载，取决于未来使用的协议；模型 API、源码同步和构建产物是否经过该链路也需另行测量。

10 Gbps 即理论单方向 **1.25×10⁹ B/s**。只计正文、不计排队和协议时，一个副本的理想串行发送时间约：1 KiB **0.819 µs**、4 KiB **3.277 µs**、32 KiB **26.214 µs**、2 MiB **1.678 ms**。这是物理发送时间下界，不是实测 RTT，也不是应用端到端时延。传播、协议、服务器与交换机处理、排队和对端调度都需要额外测量。

### 扩展并发和突发

有足够真实批次后，复制真实事件轨迹作为**负载重放假设**，保持每条消息大小和每次扇出及时间相关性，分别测试：

1. 独立团队错峰启动，按随机种子记录各批次偏移；
2. 多个团队同时遇到集成、测试失败等事件造成同步突发；
3. 改变 Agent 在服务器上的放置，分别计算目标单链路上下行副本。

例如先比较 1、10、100、1,000 个并行工作流，保留真实单次事件序列，观察 1 秒、100 毫秒滑动窗口和平均负载。达到多少并发才接近 10 Gbps，必须由采集到的轨迹计算；多次同一小任务叠加是压力重放，不是一个浏览器项目自然需要几千个 Worker。扩大 Agent 后消息率、Topic 订阅者、依赖结构和模型资源可能变化，不能把简单线性扩展当成已验证结果。

下一步可用每个方向各一个 10 Gbps FIFO 队列，在保留到达时间的前提下模拟串行化和排队，明确设置缓冲区、溢出及背压策略，输出队列长度、排队时延和丢弃数。需要比较自然负载、错峰和同步突发；这属于**离线推演**，不代表实网测试。当前一键脚本还没有实现轨迹重放、滑动窗口或该队列模拟，不应报告这些推演为实测。

对于很多小消息，即使正文速率远低于 10 Gbps，也可能因每秒连接/请求、订阅匹配、复制和唤醒次数使中继 CPU 或包处理先饱和。应报告事件/秒、扇出副本/秒、正文大小分布、Leader 与中继 CPU、延迟和错误，再在目标服务器改变中继 CPU 或改变路由实现对照。软件中继与交换机卸载需要实现相同订阅、动态更新、交付及故障语义后对比，不能只用本机 CPU 或消息字节证明交换机卸载必然更快。

## 5. 如何使用已有一键入口

在 Mac 完整仓库的 `02-Dillo浏览器/Mac/` 双击 `一键启动.command`。先检查系统是否接电、磁盘空间与内存压力，然后运行一次；结束后打开自动生成的报告，并查看 `记录/每Agent资源.csv`、`记录/系统内存采样.csv`、`记录/消息明细.csv`、`记录/每秒通信速率.csv` 与原始路由事件。保持条件不变后重复运行。失败批次留存错误和现有证据，不能算作完成的有效样本。

本版本新增的系统采样和方向统计已经纳入脚本；以上 10 Gbps 扩展与离线队列是后续分析设计，尚无真实 Mac 或跨服务器测量结果。模型调用可能产生费用；完整消息和会话可能含敏感信息，默认仅保存在本机实验目录。
