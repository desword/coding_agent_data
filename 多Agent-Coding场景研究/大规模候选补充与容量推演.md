# 大规模 Coding Agent 应用：补充检索与容量推演

检索日期：2026-11-16。本轮找到 **2 个待实测潜力项目**：Cursor 的浏览器开发和 Cursor 自身界面迁移。它们属于同一家公司的同一类长任务实践，不能当作两个独立组织的验证。另找到有公开真实协调记录的 Pepin 编译器和 ari-ai 安全平台，用作实测内容对照。

这里的“潜力项目”表示公开案例有具体应用、层级协调和大规模协作依据，值得进行有针对性的观测；它们尚未证实带宽、包处理或 Leader CPU 是瓶颈。沿用 [筛选清单](后续备选项目清单.md) 的普通服务器标准。**已通过通信瓶颈实证的项目仍为 0。**

## 证据来源

Cursor 的原始工程文章是 [Scaling long-running autonomous coding](https://cursor.com/blog/scaling-agents)。本次环境无法直接访问原文，以下关于原文的事实来自两份可访问的二次材料：[公开长任务综述](https://github.com/Pines-Cheng/blog/issues/173) 和 [JetBrains 项目中的调研记录](https://github.com/JetBrains/ytdb-slate/issues/361)。两份材料讨论的是同一 Cursor 原文，不是两次独立实验；精确数字以原文和后续原始资料复核为准。本文不将二次材料说成直接阅读到的 Cursor 原文。

公开综述描述 Cursor 使用分层 Planner、Worker 和阶段性 Judge：Planner 划分任务，Worker 专注执行与提交；后续设计演进移除了 Judge 和中央 Integrator。项目中存在 Planner/Worker 的分工，但**并非所有 Agent 消息都经过一个 Leader**。JetBrains 的调研记录提到早期中央执行者/集成者出现过载；该现象是协调或集成层面的瓶颈，具体 CPU、网络带宽、数据包和模型等待没有公开量化。

## 1. 浏览器开发：优先调查

**具体应用。** 从零开发 Web 浏览器。公开综述称实验运行约一周、生成超过 100 万行、约 1,000 个文件，并描述数百个 Worker 同时工作、向同一分支提交。JetBrains 调研也记录了浏览器和约 100 万行、1,000 文件。代码行数和文件数是代码规模，不是消息数量、正确性证明或网络流量。

**为什么有研究潜力。** 浏览器需要解析、渲染、布局、网络和测试等相互关联的模块；接口或依赖变化会影响多个工作项。大规模开发中，任务派发、完成状态、跨模块变更、冲突反馈和集成都可形成协调事件。这里的模块划分与 Topic 示例是按浏览器工作内容设计的实验映射，不是对 Cursor 原始任务列表或原生 Topic 的描述。

**Leader 三项功能的对应关系。**

| 功能 | 可研究的事件 | 原始案例与实验边界 |
|---|---|---|
| 按 Topic 分发 | 模块接口变更分发给相关开发与测试任务；任务变化时更新订阅 | Topic、集中路由及全部经 Leader 转发是实验扩展；是否订阅必须由实际依赖关系决定 |
| 跟踪依赖与触发 | 编译、接口和测试前驱到齐后触发后续任务 | 真实依赖要从任务图或测试结果采集；不能把每次提交都当作一次依赖事件 |
| 汇合与仲裁 | 汇总失败结果、候选修复与测试状态，交由软件或模型决定返工及集成 | 交换机只研究可表达的状态更新、计数和转发；代码语义判断不归入包处理 |

**筛选判断。** 这个案例具有本轮最强的单项目 Agent 数量依据，并且有中央协调/集成曾过载的过程依据，值得优先测量。公开材料没有每秒消息、消息大小、数据包数、Leader CPU、链路和模型资源，不能从代码规模推断通信量。原始实现及可运行源码本轮未找到；复现需要另选开源浏览器项目，并依据公开工作方式构造实验，产物属于适配案例。

## 2. Cursor 界面从 Solid 迁移到 React：第二顺位

**具体应用。** Cursor 自身代码库的界面迁移。上述公开综述描述了一个约 3 周的 Solid→React 原地迁移，修改量为约 +266K / -193K 行，并称通过 CI 和早期检查。它是具体的软件维护任务；修改行数不是消息字节。二次材料没有给出该迁移各阶段的 Agent 数、任务事件或网络轨迹，不能把浏览器案例的数百并发直接套用到它。

**为什么有研究潜力。** 界面迁移可能使公共组件、类型和交互接口影响多个页面与测试，适合观察变更通知、测试失败反馈、跨模块依赖与集成。按实际影响范围形成订阅和结果汇合是可研究的扩展；是否发生扇出及扇出大小取决于具体迁移记录。

**筛选判断。** 该任务拥有大范围改动和公开的 Cursor 长任务上下文，但项目级 Agent 并发和事件率尚缺。优先级低于浏览器案例。原应用代码和逐次协作记录未公开，重现时需要选择具体开源应用的 Solid 前端，迁移到 React 并保持测试及行为一致；这会产生一个新的适配实验，不是原案例重放。

公开综述还提到 Java LSP、Windows 7 模拟器和 Excel 类应用，但没有提供足以核实各自具体任务、并发 Agent 与协调路径的材料。本轮不把它们加入候选。

## 普通服务器推演：看达到瓶颈需要什么条件

沿用 Worker 服务器 **16 vCPU、64 GiB、10 Gbps**、留出系统资源后假设每台容纳 24 个 Worker；Leader 单独使用 **16 vCPU、10 Gbps**，以 **12.8 核即 80% CPU** 为水位。Worker 平均 0.5 vCPU、1 GiB 是规划假设；模型、构建、测试、共享存储的服务容量与成本另计，当前未测。

以下不是 Cursor 观测值：假设每个 Worker 平均每秒生成 `r` 个需要 Leader 处理的协调事件，每个事件发送给 Leader 后，再由 Leader 按真实订阅关系发送给 `f=4` 个接收者；每次传输正文 4 KiB。每个事件共计 1 次入向和 4 次出向消息。此处不含订阅维护、响应、重试或协议开销，也不假设代码和产物正文都经 Leader。

| 活跃 Worker | 最少 Worker 服务器 | 假设事件频率 | Leader 收入 / 发出消息数每秒 | Leader 单向出口正文 | 按入向和发出消息逐条计费的 CPU 阈值 |
|---:|---:|---:|---:|---:|---:|
| 100 | 5 | 每 Worker 每 10 秒 1 次 | 10 / 40 | 1.31 Mbps | 256 毫秒/消息 |
| 100 | 5 | 每 Worker 每秒 1 次 | 100 / 400 | 13.11 Mbps | 25.6 毫秒/消息 |
| 1,000 | 42 | 每 Worker 每 10 秒 1 次 | 100 / 400 | 13.11 Mbps | 25.6 毫秒/消息 |
| 1,000 | 42 | 每 Worker 每秒 1 次 | 1,000 / 4,000 | 131.07 Mbps | 2.56 毫秒/消息 |
| 5,000 | 209 | 每 Worker 每秒 1 次 | 5,000 / 20,000 | 655.36 Mbps | 0.512 毫秒/消息 |

CPU 阈值 = `12,800 / (Worker数 × r × (1 + f))` 毫秒/消息。按“入向消息与每个出向副本具有相同平均 CPU 成本”的简化假设，该成本达到阈值时使用 12.8 个 CPU 核；真实处理可能按事件或按连接计费，需要实际剖析。该值不是实测每包成本，也不包括模型等待时间。网卡和链路在载荷之外还有协议开销，但无法由逻辑消息数直接得出线上的包数。

**判断：** 即使 1,000 Worker 每秒各发 1 个事件、每次实际扇出 4 人，4 KiB 正文的单向出口也仅约 131 Mbps；该假设本身还没有公开轨迹支持。10 Gbps 带宽在这个量级不会先满。Leader 消息处理是否先饱和，取决于实际每秒事件、扇出和 CPU 成本；例如上述条件下，平均每条收发消息若消耗 1 毫秒 CPU，约占 5 核，若消耗 3 毫秒则约需 15 核。这是条件计算，不是预测测量。

1,000 Worker 的 42 台服务器、一个共享 Leader 和足量独立模型服务都是实验部署假设，不是 Cursor 公开实际部署。真实应用并发、模型配额和构建队列不足时，不能通过重放结果宣称实际 Coding 工作流会触发这个瓶颈。交换机卸载还需考虑可解析的报文、加密、去重、可靠交付及订阅状态一致性。

## 真实协作记录对照：Pepin / Lucy 编译器

[Pepin](https://github.com/matthewjameswatkins1978-cyber/pepin/tree/e70693938e530177b793b5219addf3d797210e6d) 是开源编译器和语言工具。[公开协调帖](https://github.com/matthewjameswatkins1978-cyber/pepin/issues/16)有 Agent 1 作为 campaign integrator、Agent 2 负责原生编译器后端、不同工作目录、所有权声明、测试与交接；页面中部分评论标记 `ChatGPT Codex Connector`，也有 Agent 间讨论。帖子标题提及四 Agent，但本次抽样只对所见评论和角色作判断。GitHub 板和人工协调存在，不能说这些消息都经 Agent Leader 转发。

2026-11-16 对页面直接可见的 GitHub 嵌入 JSON 去重统计，`totalCommentsCount` 为 **1,520**。页面载入首尾 **31 条**，中间评论没有在该页面载入；这 31 条 Markdown 正文为 **56,825 UTF-8 字节**，中位数 **1,292 字节**，最大 **3,610 字节**，其中 **14 条**标记由 `ChatGPT Codex Connector` 发表。这些是 GitHub 保存的评论正文，不能据此求整个帖子的字节、Agent 调用、实际送达或网络流量。

其中 2026-11-09 可见的 16 条在 01:40:09–03:46:52 UTC，合计 39,722 字节；该可见片段内最密集的 1 小时为 **14 条**。如果把这 14 条全部假设为不同逻辑协调事件，并复制到 6,000 个独立工作流、每条 4 KiB、向 4 个接收者发送，则 Leader 的出口正文约 **3.06 Mbps**。这不是原始网络测量，也不是完整帖子全局峰值；帖内评论有人工、角色状态、审查和结果等多种用途，不能全等同 Worker→Leader 消息。

**判断：** 它提供了具体 Codex 协作内容与可复核记录，适合作为消息内容、结果汇合和追踪方法的对照；当前观测的密度不支持把它列为高通信压力候选。

## 真实 Leader 与消息路由对照：ari-ai 安全平台

[ari-ai](https://github.com/adamissac/ari-ai/tree/a49bbe4e15f297737ccc354141482cc92ec6acde) 是正在建设的代码分析与安全平台；其中用于开发该应用的 Coding Agent 与应用运行时安全 Agent 是两组不同对象。[开发协调协议](https://github.com/adamissac/ari-ai/blob/a49bbe4e15f297737ccc354141482cc92ec6acde/coordination/PROTOCOL.md) 规定工作声明、状态、依赖冲突、评审、集成与 GitHub 消息格式。真实 [Agent 通信帖](https://github.com/adamissac/ari-ai/issues/559) 包含 Devin 的 `integration-lead → all`、Worker 向 Lead 报告阻塞、评审及完成信息；[共享看板](https://github.com/adamissac/ari-ai/blob/a49bbe4e15f297737ccc354141482cc92ec6acde/coordination/AGENT_BOARD.md) 同时列有 Codex 审查、Devin 开发及 integration-lead 等角色状态，状态列表不能等同同一时刻的活跃进程数。

这是明确的真实应用开发与 Lead/Worker 协调证据；消息也可发给所有人或直接发给其他角色，原始模式不是所有消息经 Lead 中继。路径、接收角色和 `BLOCKED` 等状态可以用于实验性 Topic 路由与依赖跟踪。

2026-11-16 页面 JSON 显示帖子共有 **210 条评论**，本次仅加载首尾 **30 条**，正文合计 **18,221 UTF-8 字节**、中位数 **513.5 字节**。可见评论中最密集的一小时有 **10 条**，不代表完整帖子全局峰值。假设 6,000 个工作流分别以此速率发送 4 KiB 消息且每次向 4 个订阅者分发，Leader 单向出口正文约 **2.18 Mbps**；入向和出向合计约 83.3 条/秒，16 vCPU Leader 在 80% CPU 水位的平均处理成本阈值为 **153.6 毫秒/收发消息**。这是强制集中、扇出和同步扩展的条件计算，评论不等于真实网络包。

**判断：** 该案例的协作语义和可观测性优于只描述角色的项目，但这段可见记录的消息密度不能支撑高通信压力预期；作为路由和交接的对照，不补入高压力候选。其代码仓库标注专有许可，后续复现实验需遵循该仓库许可。

## 建议下一步

先围绕浏览器候选寻找更接近原始事实的公开任务日志或可复现任务；若无法获得原始日志，就选定开源浏览器软件，以公开层级模式执行并明确标注适配。首次实验应抓取自然产生的任务分发、依赖更新和结果消息，分别测量 Worker 资源、Leader 每事件 CPU、实际字节/包数和模型/构建队列，再用真实分布判断是否值得扩展并发或做重放。优先验证处理瓶颈，不能将模型推理延迟或 Git 大文件流量自动算成 Leader 网络瓶颈。
