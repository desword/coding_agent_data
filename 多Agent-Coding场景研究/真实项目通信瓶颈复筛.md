# 多 Agent 开发项目：通信瓶颈复筛

检索和分析日期：2026-11-16。要求：具体开发项目；Codex、Claude Code 等真实 Coding Agent；协调者与相关联的 Worker 任务；能测量或合理推演出通信压力，并验证计算资源不会先成为瓶颈。

**结论：本轮找到 1 个具有公开实测协调事件的优先项目；没有找到 10 个已证明跨服务器通信大概率成为主要瓶颈的项目。** 下文列出已证实的事实、可计算的压力情景和无法跨越的数据缺口。此前的 [10 个具体开发项目](10个具体开发项目.md)仍是开发案例库，不是“10 个已通过通信瓶颈筛选”的清单。

## 1. 优先项目：房间预订 API 的并行功能开发

### 应用和工作模式

[Médula 的房间预订 API 开发实验](https://github.com/JoaquinRuiz/medula/blob/55b37b16237d7e1201955f05f714f3aec05141cf/README.md) 包含具体的 `demo-app`，并以 Claude Code 执行六项相互关联的功能开发和验证：

| 任务 | 具体开发内容 | 关联 |
|---|---|---|
| T1 | 登录增加 TOTP 二次验证 | 改变登录接口 |
| T2 | 增加 CSV 导出 | 调用登录接口，受 T1 影响 |
| T3 | 将预订字段 `fecha` 改名为 `inicio` | 改变数据契约 |
| T4 | 增加按日期筛选预订 | SQL 查询依赖 T3 的字段 |
| T5、T6 | 修改房间/时段验证 | 可能涉及同一文件 |

项目的公开实验把 T1–T4 并行运行，再运行 T5–T6。协调者是 Médula 软件服务而非模型 Leader：Agent 进行写操作前，通过 hook 向协调服务请求判断；写完再触发通知，服务维护其他 Agent 的工作状态并生成待接收通知。具体机制见 [SPEC](https://github.com/JoaquinRuiz/medula/blob/55b37b16237d7e1201955f05f714f3aec05141cf/medula/SPEC.md)。这与“多个 Worker 围绕同一应用的共享契约开发”匹配。

原实验由 [run_mode.sh](https://github.com/JoaquinRuiz/medula/blob/55b37b16237d7e1201955f05f714f3aec05141cf/bench/run_mode.sh)在 `127.0.0.1` 启动协调服务。**原实验没有跨服务器通信。** 把 Worker 与协调服务拆到不同服务器是可设计的实验扩展；原项目有动态通知和邮箱，但本轮没有证据表明它使用了我们所说的 Topic。

### 从作者公开数据直接得到的结果

本轮下载并只读分析了固定版本的五份 `medula.db`。原始运行结果、代码与 SQLite 均由项目公开；[summary.csv](https://github.com/JoaquinRuiz/medula/blob/55b37b16237d7e1201955f05f714f3aec05141cf/results/summary.csv)记录工作流总耗时。下表为数据库的 `decisiones` 行数和时间窗口统计；一次内部慢路径也会单独记为一行，不等同于一次 Agent 网络消息。

| 运行 | 决策记录 | 第一条到最后一条记录 | 任意 1 秒最多记录 | 任意 60 秒最多记录 | `notify` 决策耗时中位数 |
|---|---:|---:|---:|---:|---:|
| d2 | 117 | 393.7 秒 | 4 | 26 | 282.9 毫秒 |
| d3 | 119 | 364.7 秒 | 4 | 34 | 286.4 毫秒 |
| d4 | 117 | 415.8 秒 | 4 | 30 | 279.5 毫秒 |
| f2 | 104 | 271.2 秒 | 4 | 35 | 3,100.9 毫秒 |
| f3 | 111 | 260.7 秒 | 4 | 31 | 3,110.9 毫秒 |

`notify` 的 `latencia_ms` 是协调服务侧决策耗时；决策涉及模型调用，不能当成网络延迟。不同运行使用不同决策模型，不能据此仅归因于网络。1 秒和 60 秒窗口按记录 `ts` 计算，是决策记录速率，不是 TCP 包速率。

以 [f3 数据库](https://github.com/JoaquinRuiz/medula/blob/55b37b16237d7e1201955f05f714f3aec05141cf/results/runs/f3/medula.db)为例：

- 项目记录的完整运行耗时为 **276.5 秒**；111 条决策记录由 **69 条 acquire、35 条 notify、7 条 lento 慢路径**组成。
- 数据库中有 **15 条已标记投递的邮箱记录**，文本合计 7,682 UTF-8 字节；这不是网络抓包或完整业务消息总量。
- 把 69 + 35 条主类型决策记录除以总运行时间，得到约 **0.376 条/秒/工作流**。该值是日志速率，不保证每一行严格对应一次网络请求。
- f3 的 acquire 决策耗时中位数约 **2.45 秒**，notify 约 **3.11 秒**。这两个数包含服务端决策和模型相关耗时，不能称为跨服务器通信耗时。

f3 中数据库保存的 `estado_enviado` 等是协调器发给决策模型或内部记录的状态，不自动等于 Worker 发给 Leader 的字节。Leader–Worker、Leader–模型、共享文件和 Git 等流量必须分开测量。

### 通信压力推演

以下是**条件计算，不是公开实测**：

1. 假设大量工作流都保持 f3 的平均主类型记录速率 `104 / 276.5 ≈ 0.376 条/秒`。
2. 假设每条记录对应一次跨服务器控制请求，且所有工作流共享同一个协调端点。
3. 假设每个请求正文和每个响应正文各 4 KiB，完整发送；暂不计协议、重传和额外通知。

| 同时运行的工作流 | 假设请求数/秒 | 假设单方向正文流量 |
|---:|---:|---:|
| 1,000 | 约 376 | 约 12.3 Mbps |
| 10,000 | 约 3,761 | 约 123.3 Mbps |
| 100,000 | 约 37,613 | 约 1.23 Gbps |
| 约 811,000 | 约 305,000 | 约 10 Gbps |

表中输入和输出按全双工分别计算；若请求与响应分别都是 4 KiB，每个方向的正文流量分别接近表值。该计算没有将两方向直接相加后与单方向带宽比较。4 KiB、共享协调端点和“每条记录一次请求”都不是 f3 的实测条件；它们只用于看量级。

**判断：原始预订应用适合作为高频协调事件研究对象，但没有证据表明其实际规模容易打满 10 Gbps。** 若只用几千个此类工作流，先达到限制的可能是协调服务、模型或 Worker 的计算/并发能力；目前没有对应容量数据，无法给出真实瓶颈。数万个以上真实工作流共享一个协调端点属于需要证明的部署假设。

例如，若人为假设 10,000 个工作流共享协调服务、约 3,761 次决策/秒，且每次决策平均占用模型服务 2.5 秒，则按照 Little 定律需要约 **9,403 个并发中的决策**。2.5 秒在此作为假设，不是从上述中位数推导的平均值；实际模型批处理和并发容量必须实测。这个数量说明模型服务可能比网络更早成为约束，不能仅把 Worker 从模拟器改为进程就排除其他瓶颈。

## 2. 账单分析应用：通过开发模式筛选，不通过高通信压力证明

[Expense App](https://github.com/hanco1/expense-app-loop-built/blob/62ec296b49fa17aac73fb8feb9261dcf79b5fda3/README.md)是 Codex 多角色开发的具体应用，公开产品、后端、前端和 review 的协作记录。对固定版本 `docs/loop/messages/` 的 89 份文件统计：

- 记录时间跨度 270,805 秒，平均约 **0.000329 条文件记录/秒**；单条记录的最大 60 秒窗口为 2 份、最大 1 小时窗口为 18 份。
- 89 个 UTF-8 文件合计 320,705 字节，包含元数据；这些文件不是网卡流量，日志可能不完整，记录时间也包含人工和开发等待。
- 即使假设 **100,000 个工作流**以相同全周期平均速度运行、所有记录都通过同一个 Leader 并各复制给 4 个接收者，仅按文件大小估算，Leader 出口正文约 **3.79 Mbps**。四接收者和集中中继是人为假设，原记录并未证明；这个算式不代表网络实测或峰值。

**判断：该项目有真实 Coding 分工和记录，适合研究交互内容；不能用现有公开记录证明大规模通信或网络瓶颈。** 它不应作为“高流量已得到验证”的主证据。

## 4. 后续实验必须证明的容量关系

对每个测试负载先测各资源的可持续容量，而不是只增加 Worker 数。设 `λ` 为共享协调端点的目标事件到达率：

1. **先测 Worker、构建/测试、模型服务、存储**：分别得到相同正确率和任务完成要求下的可持续容量。运行时采集 CPU、内存、GPU、模型请求排队、构建队列和错误率。
2. **测协调与网络**：记录 Leader 每秒逻辑事件、实际请求、包、单方向字节、网卡与交换机端口、队列、丢包、CPU 和 P50/P95/P99。记录真实拓扑、是否跨服务器、连接复用和协议开销。
3. **确认存在有效区间**：目标 `λ` 必须低于 Worker、模型、存储等层的实测可持续容量，且达到被研究的 Leader 或网络的可持续容量。容量要有实测余量；若不存在这个区间，就不能声称通信是主要瓶颈。
4. **做干预对照**：在工作量、消息内容和语义一致时，分别调整 Leader CPU、网卡/链路带宽以及消息处理方式。如果增带宽改善吞吐和尾延迟，支持带宽瓶颈；如果改善来自提高 Leader CPU 或卸载每包/事件处理，支持服务器处理瓶颈。模型/Worker 排队变化需要同时核对。
5. **区分真实运行和重放**：真实 Agent 轨迹用于建立事件率与载荷分布；重放可单独提高负载并隔离计算，但重放只能证明系统在该合成到达率下的表现，不能证明真实生产会达到该流量。

若按真实记录扩展后仍需几十万并发工作流才可能接近链路上限，就必须证明该并发规模、共享 Leader 的部署和充足的模型/Worker 容量；不能将它作为已存在的业务事实。

## 5. PiggyLead 能处理的范围

房间预订任务中可以研究：按工作流/任务标识路由通知；维护固定依赖的完成状态；在条件满足时触发后继；将结构化裁决或结果到齐通知转给软件组件；按动态订阅关系转发通知。Topic 和跨服务器路径是实验扩展，需记录新增工作量和状态更新。

冲突的代码语义判断、补丁正确性和模型仲裁仍在服务器/Gateway；模型流量不属于交换机自动消除的 Agent 消息。原项目通过 HTTP 本地环回调用，远程运行时还要设计可解析的协议和可靠性/去重机制。若消息经过 TLS，交换机不能直接读取加密负载；若 Topic 和工作流状态频繁变更，还要验证规则更新、状态容量和一致性。按现有 PiggyLead 文档，当前原型的一个 32 位依赖位图最多跟踪 32 个依赖相关前驱，不能直接宣称无限 Agent 扩展。
