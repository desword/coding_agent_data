# 01 · 房间预订 API：多 Agent 协调实验计划

> 定位更新：该项目保留为已安排的真实协调机制基准；按 [普通服务器容量推演](../后续备选项目清单.md) 的公开事件速率与假设，它尚未通过“通信大概率成为瓶颈”的候选筛选。真实多 Agent 一键测试尚未实现。

## 固定案例

首个实验采用 [Médula](https://github.com/JoaquinRuiz/medula/tree/55b37b16237d7e1201955f05f714f3aec05141cf) 的房间预订 API，固定版本 `55b37b16237d7e1201955f05f714f3aec05141cf`。原项目用 Claude Code 执行六项相关开发任务：登录加二次验证、CSV 导出、预订字段改名、日期筛选，以及两项同文件验证修改；前四项并行、后两项并行。协调服务负责写入前判断、写入后通知与冲突等待。

应用是 `demo-app`；它不是让用户选择的项目。原项目的协调服务是软件组件，承担部分 Leader/Orchestrator 职责。原版通过本机环回地址通信，跨服务器部署和 Topic 路由都是后续实验扩展。

## 已完成的基线

2026-11-16，在 Linux、Python 3.12.14 下，从固定版本检出应用、协调服务与 `tasks/`，分别运行原版测试：

| 验证 | 结果 | 范围 |
|---|---|---|
| `demo-app` 测试 | **15 项通过** | 房间预订应用的原版功能测试 |
| `medula` 测试 | **90 项通过** | 协调服务和 hook 等测试；模型调用使用测试替身 |
| 作者 f3 历史记录分析 | **111 条决策记录** | 公开数据库，不是本轮新运行 |

第一次提取源码时漏掉 `tasks/`，协调服务有 3 项测试失败；补齐原版任务文件后重跑全部 90 项通过。结果见上表。该基线尚未启动真实 Claude Code Worker，也没有测跨服务器通信。

## 按顺序执行的实验

### 阶段 1：原生真实开发基线

- 固定上述版本和原来的六个任务，在独立批次目录恢复工作副本；每批记录应用变更、测试结果、Agent 会话和协调数据库。公共依赖放在 `工具缓存`，批次结果互相独立。
- 先验证 Claude Code 已安装、已登录且实际模型调用成功，再启动原版工作流。认证按用户机器的官方登录流程处理，不在报告中写入凭据。
- 保持原来的四个并行任务加后续两个任务；逐一核对 Worker 确实启动、完成实际代码修改、原项目验证结果和失败原因。没有完成就报告未完成。
- 对照作者公开的配置记录两种协调方式：C 为文件锁；F 为模型辅助判断。二者判断语义不同，结果分开报告。原版 C 的 Agent 仍需要 Claude 访问；原版 F 的协调模型还需要 OpenRouter。执行前必须按选定运行方式完成对应登录和认证。
- 正式开发耗时从首个真实 Agent 任务开始计，下载、安装、登录、历史数据分析和环境准备不计入。每个阶段在窗口显示当前工作、已耗时、最近输出和异常。

**一键入口的实现状态：尚未完成。** 上游 `bench/lib/agent.sh` 在 Agent 启动时使用 `--permission-mode bypassPermissions`，并在独立工作区运行；不能直接将这个上游脚本包装为默认的本地双击实验。实现入口前，需要保留隔离工作区并验证适合用户机器的权限、依赖安装、认证与退出清理。原项目的独立 Claude 配置可能需要上游所要求的 `CLAUDE_CODE_OAUTH_TOKEN` 或 OpenRouter 认证，普通登录能否在该隔离配置复用须实测。

### 阶段 2：本地协调事件与消息大小

- 在原生工作流能完成后，给 Worker 与协调服务的 HTTP 请求、响应及邮箱通知增加可关联的事件记录：工作流、Agent、任务、事件类型、ID、状态、发送与接收时间及序列化大小。用同一进程可比较的单调时钟测量本地时间；未捕获的字段标记未知。
- 报告分别给出逻辑事件数、正文/头部可观测字节、事件速率、扇出、P50/P95/P99 与错误。HTTP 请求往返时间含服务端处理；数据库的决策时间含模型调用，不称为网络单向延迟。
- 区分 Agent→协调服务、协调服务→Agent、协调服务→模型、Git/文件和应用业务流量。日志正文与实际链路字节、数据包个数分别计算，不作等同。
- 对比原版无观测与加观测的完成率、消息顺序和耗时，检查记录是否改变了任务行为。按原项目的锁和模型决策配置各自统计，不混算。

### 阶段 3：跨服务器与协调方式对照

- 在前两阶段完成后，将实际 Worker 与协调服务放到不同服务器；逐一记录主机、网络拓扑、服务地址、链路容量和数据路径。原项目假定同一工作目录；拆分服务器前需明确共享文件系统或版本同步，验证文件一致性和任务语义，否则该模式不成立。
- 原版路由与事件保持基线；把主题订阅、交换机转发与依赖位图设计为单独对照版本。模型的代码语义判断留在软件或 Gateway；只卸载可表达的确定性匹配、路由和状态操作。
- 端到端延迟用同主机往返或经过验证的时钟同步计算；不能从未同步的两台机器时间戳推断单向网络延迟。实际包数、线速字节和丢包必须通过网络或接口计数器获得。

### 阶段 4：在其他资源有余量时增加负载

- 先测 Worker、模型服务、构建/测试、存储、协调 CPU 和链路的可持续容量；逐级增加真实工作流，收集完成率、吞吐、排队、资源使用和 P50/P95/P99。
- 只有在 Worker、模型和存储仍有余量，而协调处理或链路先达到容量时，才能认定该轮是通信瓶颈。模型请求变慢或任务执行时间不能直接算成网络延迟。
- 根据真实消息大小和到达时间分布做独立的重放压力测试。重放可以找系统容量，但不代表真实业务已经达到该规模。明确记录丢包、错误、等待和未完成任务。

## 三项 Leader 功能的实验位置

| 功能 | 原始案例 | 后续对照 |
|---|---|---|
| 消息分发 | 写入后由协调服务判断是否通知其他 Agent，通过邮箱交付 | 增加按工作流/任务/变更类型的 Topic 订阅和路由；记录订阅变更 |
| 依赖跟踪和触发 | 原实验有冲突等待及释放；任务按两轮启动 | 将可预先确定的依赖状态及后继触发另行实现，验证结果与基线一致 |
| 结果仲裁 | 协调服务对写入冲突进行模型或锁判断 | 状态到齐和结构化裁决可研究卸载；代码语义判断仍由软件/模型完成 |

任务重新分配和代码集成的语义及结果必须单独检查；不能将包成功转发视为任务完成或代码已集成。所有统计明确区分“原版事实”和“实验新增”。
