# 多 Agent Coding：10 个公开候选与初步验证

> 本文是历史**框架与研究系统**调研，仅供背景追溯。当前有效筛选结果见 [后续备选项目清单](后续备选项目清单.md)。

检索日期：2026-11-16。筛选依据：[场景检索与评估依据](场景检索与评估依据.md)。

这 10 项来自**10 个不同仓库的框架、官方示例或研究系统候选**，并非 10 个均已证明满足所有条件的实际应用。当前没有发现能够据此证明“真实 Coding 流量已经使 Leader 的网卡或包处理饱和”的完整公开轨迹。涉及规模和压力的地方，下面明确区分公开事实、合理推导、实验扩展和待验证。

编号便于引用，不代表已测通信量排名；后面的实验顺序综合考虑真实 Coding、Leader/Worker、依赖或反馈、并发潜力及可观测性。

| 顺序 | 候选 | 公开证据中可见的开发与协作 | 对我们最有价值的特征 | 主要缺口 |
|---|---|---|---|---|
| 1 | [Agent Orchestrator](#1-agent-orchestrator) | main agent 分工；Worker 使用 worktree；CI/审查反馈 | 主流 Coding Agent、实际项目和消息接口 | Topic、实际事件速率与跨服务器路径待测 |
| 2 | [Oh My OpenAgent](#2-oh-my-openagent) | 主 Agent、后台 Worker、实现/测试/审查、任务图 | 并发与依赖图的结合 | 公开能力不等于实测规模或原生 Leader 中继全部消息 |
| 3 | [OpenHands Software Agent SDK](#3-openhands-software-agent-sdk) | 软件 Agent SDK、主 Agent 委派、并行测试 | 现成并行子 Agent 压力测试和远程 Agent Server | 官方并发压力测试是模拟模型和进程内通信 |
| 4 | [Ruflo](#4-ruflo原-claude-flow) | Codex/Claude Code 编排、协调者与专门 Worker | 公开指南描述依赖协调和跨机器 federation | 实测实现、路由和性能待核实 |
| 5 | [Robin / Open SWE](#5-robin--open-swe) | 代码修改、验证、PR 审查、CI 反馈和子 Agent | 偏实际工程工作流 | 原生多 Worker 关联、通信量需具体轨迹；部署依赖需评估 |
| 6 | [Codex 原生多 Agent](#6-codex-原生多-agent) | 子 Agent 创建、消息、等待和结果返回的官方工具代码 | 用户熟悉，便于测原生通信行为 | 本轮未找到满足所有条件的现成公开应用轨迹 |
| 7 | [MetaGPT](#7-metagpt) | 软件公司角色、项目开发；环境中消息路由和并发执行 | 有明确角色与路由代码 | 当前版本与具体软件任务的并发度、流量待测 |
| 8 | [AgentVerse](#8-agentverse) | 官方代码任务有 solver、critic、manager 等角色 | 并发评论与消息广播可作为研究依据 | 官方 HumanEval 配置不是并发决策器；是函数任务，不代表真实大型应用 |
| 9 | [Oh My Codex](#9-oh-my-codex) | Codex Leader、并行 Worker、任务状态、反馈和集成 | 官方 Team 协议直接描述工作交接、阻塞重分配及 Leader 通知 | 共享状态和 mailbox 不等于跨服务器包，真实规模待测 |
| 10 | [MacNet](#10-macnetchatdev-研究分支) | 面向软件生成的多 Agent DAG，可配置拓扑并记录边的信息 | 大规模图结构及依赖传播 | 不是已验证 Leader 中继；规模宣称不等于真实服务器网络实测 |

## 1. Agent Orchestrator

- **公开事实**：[固定版本 README](https://github.com/OrchestratorInc/agent-orchestrator/blob/ca3f3646c52ff4abe9bdc4036f5c17164f783874/README.md)描述 main agent 分解工作、每个 Worker 的独立 worktree，以及 CI 失败、审查评论和冲突反馈；列出 Codex、Claude Code 等，亦介绍云工作空间。[spawn 命令](https://github.com/OrchestratorInc/agent-orchestrator/blob/ca3f3646c52ff4abe9bdc4036f5c17164f783874/backend/internal/skillassets/using-ao/commands/spawn.md)有 worker/orchestrator 角色；[send 命令](https://github.com/OrchestratorInc/agent-orchestrator/blob/ca3f3646c52ff4abe9bdc4036f5c17164f783874/backend/internal/skillassets/using-ao/commands/send.md)描述向指定会话发消息和排队行为。
- **压力推导**：多个开发任务和反馈事件可以汇聚到协调服务；关联任务的重试及审查可能产生多轮消息。可观察 spawn、send、状态与结果事件，实际速率未知。
- **扩展和待验证**：按具体工作流增加 Topic 和跨服务器部署；确认官方本地 daemon、Agent session、SCM/CI 的实际通信路径和可记录字段。不得将 UI 事件或 SCM 轮询全部当作 Worker 间消息。
- **应用选择线索**：可将其自身开源仓库和实际公开问题（如 [#75](https://github.com/OrchestratorInc/agent-orchestrator/issues/75)）用于历史问题复现，但需要确认适用的修复前版本与验证方法。将框架与该任务组合是我们的实验选择，不代表官方公开过这一多 Agent 运行轨迹。注意：官方 spawn 文档中“issue 142/session leak”是命令示例；当前同编号页面是另一 PR，不能将它直接当成真实的对应缺陷。

## 2. Oh My OpenAgent

- **公开事实**：[固定版本编排指南](https://github.com/code-yeongyu/oh-my-openagent/blob/7d727617f2a3360125d3da530dbcd165e69304fd/docs/guide/orchestration.md)称主 Agent 负责协调，使用 `task` 委派实现、测试和 QA，后台任务可并发，`mass-ulw` 使用依赖图，Worker 向主 Agent 返回结果和证据；[README](https://github.com/code-yeongyu/oh-my-openagent/blob/7d727617f2a3360125d3da530dbcd165e69304fd/README.md)描述图式并行任务。
- **压力推导**：多 Worker 并行返回结果，以及依赖图分阶段触发，具备汇聚、触发和多轮反馈的研究潜力。README 的“大量 Agent”是项目能力描述，不是本轮核实的实际网络测试。
- **扩展和待验证**：选定公开开发任务并捕获真实轨迹；核实具体通信通道和是否支持远端 Worker。不能假设所有 Agent 消息都经过 Leader。

## 3. OpenHands Software Agent SDK

- **公开事实**：[SDK README](https://github.com/OpenHands/software-agent-sdk/blob/d5c17fea9c6b594f5c92284a7c46fee03217a6f4/README.md)面向代码工作，提到多 Agent 重构和 Docker/Kubernetes Agent Server。[委派示例](https://github.com/OpenHands/software-agent-sdk/blob/d5c17fea9c6b594f5c92284a7c46fee03217a6f4/examples/01_standalone_sdk/25_agent_delegation.py)是主 Agent 并行委派并汇总结果，但具体任务是旅行规划，不能称为 Coding 案例。[官方压力测试](https://github.com/OpenHands/software-agent-sdk/blob/d5c17fea9c6b594f5c92284a7c46fee03217a6f4/tests/agent_server/stress/test_parallel_subagents.py)检查并行子 Agent 和内部发布订阅；[预算](https://github.com/OpenHands/software-agent-sdk/blob/d5c17fea9c6b594f5c92284a7c46fee03217a6f4/tests/agent_server/stress/budgets.py)设置 8 个子 Agent。
- **压力推导**：基于代码 Agent SDK，将其委派机制用于真实公开代码任务，可以研究并行返回和共享协调。该组合与并发扩展属于实验设计，需实测。
- **限制**：官方压力测试使用模拟 LLM 和进程内 ASGI，不是真实 Agent 代码开发，也没有真实网络。Agent Server 可用于研究远程服务，但不能假定当前每个子 Agent 天然独立跨服务器。

## 4. Ruflo（原 Claude Flow）

- **公开事实**：[固定版本 README](https://github.com/ruvnet/ruflo/blob/3a1479883b55b7f786ef0bf3141478e4dfb9444f/README.md)将其称为 Claude Code 与 Codex 的编排 harness，并给出检查仓库、编写测试的示例；[官方指南](https://github.com/ruvnet/ruflo/blob/3a1479883b55b7f786ef0bf3141478e4dfb9444f/docs/ruflo-explained.md)描述协调者、任务依赖、结果汇合和不同机器间 federation。
- **压力推导**：多角色开发与跨机器消息的组合值得研究；指南中的 federation 是项目文档对功能的描述，不是本轮实测的吞吐结果。
- **待验证**：跨机器协调的实际执行路径、权限与版本要求、是否有中心中继、真实 Coding 消息和依赖图行为。直接检查公开说明不代表已验证所有插件与宣称。

## 5. Robin / Open SWE

- **公开事实**：[固定版本 README](https://github.com/langchain-ai/open-swe/blob/f73960b482435e635348ec4bdd85ecee49e720bc/README.md)描述实现、验证、PR 审查、CI 和反馈，使用 subagents 并行调研与独立工作；线程工作可并行，编码运行在隔离 sandbox。
- **压力推导**：多个 PR、反馈循环和并发工作流可能形成共享协调事件；是否由同一服务汇聚、实际关联程度需要测量。
- **限制**：项目说明按原样部署需要 Managed Deep Agents，否则建议 fork 适配运行环境。Topic、具体真实流量和多 Worker 结果汇合均未在本轮证实。

## 6. Codex 原生多 Agent

- **公开事实**：[官方工具定义](https://github.com/openai/codex/blob/2309bae1ae7a6dcab6dd0ade0fd37a7491b1de01/codex-rs/core/src/tools/handlers/multi_agents_spec.rs)定义 spawn、send 和 wait 等 Agent 管理与消息工具；源码描述子 Agent 可接收任务并返回结果。
- **压力推导**：可以在公开代码任务中实际采集任务分派、消息和结果事件，并逐步提高并发。应用、任务分工和并发配置需要明确标为实验选择。
- **限制**：这是原生框架能力证据；本轮未找到对应的现成公开应用轨迹来证明高通信量、动态 Topic 或跨服务器部署。它支持的其他消息路径也不能自动算成 Leader 中继。

## 7. MetaGPT

- **公开事实**：[固定版本 README](https://github.com/FoundationAgents/MetaGPT/blob/11cdf466d042aece04fc6cfd13b28e1a70341b1f/README.md)描述产品、架构、项目管理和工程角色，并提供生成 2048 游戏的例子；[当前入口代码](https://github.com/FoundationAgents/MetaGPT/blob/11cdf466d042aece04fc6cfd13b28e1a70341b1f/metagpt/software_company.py)配置 TeamLeader、Architect 和 Engineer 等角色。[环境代码](https://github.com/FoundationAgents/MetaGPT/blob/11cdf466d042aece04fc6cfd13b28e1a70341b1f/metagpt/environment/base_env.py)通过成员地址匹配发送消息，并使用 `asyncio.gather` 运行角色。
- **压力推导**：软件角色间的交付与多轮开发有消息路由研究价值，可在多个软件任务并发时观察汇聚。
- **限制**：具体默认角色组合以代码为准，不能把 README 的全部角色都当作默认启用；环境内消息匹配不是已证明的跨服务器 Topic broker 或网络包。

## 8. AgentVerse

- **公开事实**：[项目 README](https://github.com/OpenBMB/AgentVerse/blob/f90c4bd9680fdd3bcff8c52c9170911a59b23478/README.md)将软件开发列为多 Agent 应用；[HumanEval 配置](https://github.com/OpenBMB/AgentVerse/blob/f90c4bd9680fdd3bcff8c52c9170911a59b23478/agentverse/tasks/tasksolving/humaneval/gpt-4/config.yaml)包括角色分配、solver、critic、manager 与代码测试。[并发决策器代码](https://github.com/OpenBMB/AgentVerse/blob/f90c4bd9680fdd3bcff8c52c9170911a59b23478/agentverse/environments/tasksolving_env/rules/decision_maker/concurrent.py)并行执行评论并广播消息。
- **压力推导**：函数实现与多评论者反馈可以研究一对多和多对一；工作流并发或将并发决策器用于特定任务需要实验适配。
- **限制**：给出的 HumanEval 配置使用 `vertical-solver-first`，并不是上述并发决策器；HumanEval 是函数级基准，不代表真实大型应用。任务与决策器的组合须标为实验扩展。

## 9. Oh My Codex

- **公开事实**：[固定版本 README](https://github.com/Yeachan-Heo/oh-my-codex/blob/c860bc0b9d486f492536832996c2ae86cdda2ad2/README.md)将其定位为 Codex CLI 工作流层，描述 Leader、`omx team` 并行 Worker、各自 worktree，以及结果向上汇报，并提供 `omx team 3:executor "fix the failing tests with verification"` 示例。[Team 协调协议](https://github.com/Yeachan-Heo/oh-my-codex/blob/c860bc0b9d486f492536832996c2ae86cdda2ad2/docs/team-coordination-protocol.md)将任务依赖、交接、阻塞重新分配和 Leader 更新列为协调条件。
- **压力推导**：相关 Worker 的多轮反馈、交接与结果汇聚可形成协调事件；多个 Team 并发可研究共享协调压力。要先确认事件如何被实际记录，以及是否汇聚到同一服务。
- **限制**：官方示例是通用修复测试的提示，不是已核实的某一公开应用运行轨迹；协议提及 task JSON、inbox 和 mailbox，这些共享状态不自动构成网络消息。Topic、跨服务器和高并发包流需要适配与实测。官方与 Oh My OpenAgent 是不同项目，但有关联的工作流思路，比较时需注明。

## 10. MacNet（ChatDev 研究分支）

- **公开事实**：[MacNet 固定版本 README](https://github.com/OpenBMB/ChatDev/blob/e7a35824fd683ffe8fc237e28ecc47d7b1a5da63/README.md)描述可配置多 Agent DAG、软件生成任务、节点之间的代码变化及日志；[论文](https://arxiv.org/abs/2406.07155)研究多 Agent 协作规模。README 提供五子棋生成命令。
- **压力推导**：多前驱汇合和图上传播适合研究依赖跟踪及消息分发；拓扑和任务数量可作为压力测试变量。
- **限制**：MacNet 是 ChatDev 同仓库的独立研究分支，而非独立项目仓库；其拓扑不自动等同于 Leader 中继。公开的大规模能力声明不证明同规模真实 Coding Agent、跨服务器网络或包处理实测。

## 已开始的本地机制验证

在 Linux / Python 3.13.5 上，检出 OpenHands Software Agent SDK `d5c17fea9c6b594f5c92284a7c46fee03217a6f4`，运行其原版 `tests/agent_server/stress/test_parallel_subagents.py`，结果 **1 passed in 5.10s**。测试采用 8 个模拟子 Agent，检查各子 Agent 完成、并发性和部分资源断言；产生若干依赖弃用警告。首次运行缺少 `pytest-forked`，补齐测试依赖后通过。

原测试说明明确：使用模拟 LLM、进程内 ASGI，**没有真实模型、真实网络或真实软件开发流量**。所以该结果仅证明当前环境中该官方机制测试通过，不能作为 Leader–Worker 带宽、网络延迟或 Coding 任务成功的结果。

同时尝试运行 Agent Orchestrator `ca3f3646c52ff4abe9bdc4036f5c17164f783874` 的[协调消息接收确认测试](https://github.com/OrchestratorInc/agent-orchestrator/blob/ca3f3646c52ff4abe9bdc4036f5c17164f783874/backend/internal/session_manager/send_confirm_coordination_integration_test.go)。该测试使用实际 SQLite 存储，但 Worker 的部分运行组件是 fake；它可以检查确认逻辑，不是实际网络测试。当前环境已下载并校验项目要求的 Go 1.27.4，但 Go 模块代理重定向到的存储地址返回 403；其他尝试的代理也未能访问，测试未开始，尚无通过或失败结论。依赖文件保留在研究目录供重试。这是当前云环境的网络限制，不代表用户本地必然无法运行。

另尝试当前云环境的 Codex CLI 最小连通性检查；CLI 已登录，但启动时因只读文件系统无法初始化进程内 app-server。未能在该环境完成真实 Codex 多 Agent 开发运行。不能将此归因于用户本地机器，也不能将前面的模拟测试冒充真实 Coding 测试。

## 后续实验优先级

1. **Agent Orchestrator + 公开代码任务**：先固定框架和历史任务版本，确认该任务在基线能够复现，再测 Codex Worker 的实际分派、消息、审查/测试反馈；先本机测原生行为，再设计跨服务器适配。具体历史 issue 的任务拆分属于实验配置，不能说是官方已有轨迹。
2. **Oh My Codex / Oh My OpenAgent**：选择有公开依据的代码变更，实测主 Agent、并发 Worker、任务交接、依赖图及结果回传；验证其通信机制和成本后再进行压力扩展。
3. **OpenHands SDK**：在已通过的模拟机制测试之外，使用真实代码任务和真实模型采集自然轨迹，再分别设计远程通信和重放压力测试。

以上都不是已完成的一键真实 Coding 实验。新的独立实验应沿用每应用单独一键入口、公共依赖缓存与独立报告；先完成可用性和通信观测验证，再加入 Topic 或网络卸载对照。
