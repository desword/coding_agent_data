# 多 Agent Coding：普通服务器容量推演与备选清单

更新时间：2026-11-16。**通过通信瓶颈筛选的候选：0 个；待补位：10 个。** 取消 iOS 项目。上一版清单的项目均已复筛，未满足新标准的项目移出候选；不能以凑数方式补齐。已安排的[房间预订 API](01-房间预订API/README.md)保留为测量协调机制的基准，不计入通过筛选的候选。

要求是：公开资料支持具体应用和真实多 Coding Agent 协作；以可核查的事件速率、消息大小、扇出及资源容量为基础，推演在普通服务器和可信并发规模下，Leader 的网络或消息处理能够先于 Worker、模型和存储达到容量。允许把公开工作流适配到跨服务器、集中中继和 Topic，但必须标明新增行为。

## 统一服务器与计算口径

以下是筛选用假设，不是实际测得的服务器容量：

- 一台 Worker 服务器：16 vCPU、64 GiB 内存、10 Gbps 网卡；预留 4 vCPU、8 GiB，假设每个活跃 Worker 平均占 0.5 vCPU 和 1 GiB，最多可容纳 `min(12 / 0.5, 56 / 1) = 24` 个 Worker。每个工作流的 Agent 配置按项目另列；真实用量、进程峰值和任务完成率需要测试。
- 一台独立 Leader 服务器：16 vCPU、10 Gbps 全双工网卡；为了估算稳定服务，以 80% CPU 即 12.8 核计算阈值。所有工作流假设汇聚到这个 Leader，且网络链路无其他流量。网卡带宽不是实际交换路径的保证。
- 未给出消息大小的项目，统一假设每次单播请求和响应正文各 4 KiB。单方向正文速率 `R = 工作流数 × 每工作流每秒事件数 × 4096 × 8`；不计 TCP/IP、TLS、确认包、重传和通知复制。假设单方向都经 Leader，阈值比较按全双工每方向分别进行。
- 每事件 Leader 可用 CPU 时间阈值 `C = 12,800 / 每秒事件数` 毫秒。实际平均 CPU 时间超过阈值，才说明在这个事件率和配置下 CPU 超过设定的 80% 水位；事件内部的异步等待和模型响应时间不属于 CPU 时间。事件数、HTTP 请求数和网络包数不是同一个量。
- 为避免把模型服务算进 Leader 的包处理，把模型服务单独部署并假设有足够容量。它需要独立的 CPU/GPU、并发和预算；存储与构建服务也必须有余量。**它们的容量当前均未实测**，因此下表不能证明系统满足端到端瓶颈条件。

4 KiB 只是为了给出可比较量级。真实扇出、对象引用与内容传输、连接复用和包大小都会改变结果。10 Gbps 饱和公式算的是正文，线上字节会更早触及链路容量；是否先触及需要实际测量。

## 房间预订 API：机制基准，未通过瓶颈筛选

[Médula 的房间预订应用和实验](https://github.com/JoaquinRuiz/medula/tree/55b37b16237d7e1201955f05f714f3aec05141cf)：Claude Code 前四个任务并行，协调服务负责写入前判断和写入后通知；其余两个任务在下一批执行。原版在本机环回运行，不是跨服务器。原始数据和解析见 [公开轨迹分析](真实项目通信瓶颈复筛.md)。

[f3 数据库](https://github.com/JoaquinRuiz/medula/blob/55b37b16237d7e1201955f05f714f3aec05141cf/results/runs/f3/medula.db)有 69 条 `acquire` 和 35 条 `notify` 决策记录，[汇总文件](https://github.com/JoaquinRuiz/medula/blob/55b37b16237d7e1201955f05f714f3aec05141cf/results/summary.csv)给出总耗时 276.5 秒，即 **104 / 276.5 ≈ 0.376 条记录/秒/工作流**。记录不是网络请求，有内部重复或遗漏的可能；以下为了推演，假设每条记录对应一次跨服务器请求。各工作流均假设占用 4 个 Worker 槽位，因此每台 Worker 服务器可容纳 6 个工作流；模型等额外容量另行提供。

| Worker 服务器数 | 工作流数 | 假设请求/秒 | 单方向正文流量 | Leader CPU 在 80% 水位的平均成本阈值 |
|---:|---:|---:|---:|---:|
| 1 | 6 | 2.26 | 0.074 Mbps | 5,672 毫秒/请求 |
| 10 | 60 | 22.57 | 0.740 Mbps | 567 毫秒/请求 |
| 100 | 600 | 225.68 | 7.40 Mbps | 56.7 毫秒/请求 |
| 1,000 | 6,000 | 2,256.78 | 73.95 Mbps | 5.67 毫秒/请求 |
| 10,000 | 60,000 | 22,567.81 | 739.50 Mbps | 0.567 毫秒/请求 |

**判断**：在 1,000 台 Worker 服务器、6,000 个工作流集中到一台 Leader 的假设下，平均单向正文约 74 Mbps，只占 10 Gbps 的 0.74%；按这个均值与 4 KiB 请求，约需 **81.1 万个并发工作流、13.5 万台 Worker 服务器**才达到 10 Gbps 单向正文。不能据此将该应用选为容易打满普通 10 Gbps 链路的业务。

同一假设下，Leader 平均每请求若消耗 **5.67 毫秒 CPU**，则达到 80% CPU 水位；低于该值则不会由这部分请求达到该水位。这个阈值不是实测成本，且包括被计入处理的应用协调逻辑，不等同网卡包处理。服务端 `notify` 决策的约 3.11 秒中位耗时包含模型等待，不能代入 CPU 成本。

f3 的历史记录中，单工作流 1 秒最多出现 4 条决策记录。假设 6,000 个工作流恰好同秒达到该峰值、每条都形成一个 4 KiB 网络请求，则 Leader 入向正文约 786 Mbps，仍低于 10 Gbps；这是同步峰值的条件计算，不是实测并发峰值、最大速率或未来流量上限。原始运行只保存一个工作流的记录，真实峰值、实际网络包、路由成本、Worker/模型容量均待测。

在该业务上仍可测试真实写冲突通知、动态接收者、依赖状态和汇合。Topic、跨服务器及 Leader 集中转发是实验扩展；做同语义对照后才能判断可卸载的包处理或协调状态是否构成瓶颈。

## 补位办法与验收

继续检索有真实应用、主流 Coding Agent 和集中协调的公开实践，优先查找持续集成失败风暴、多仓库接口迁移、大规模安全修复、依赖图批量更新等由实际开发事件触发的工作流；每个具体项目仍必须先核查，不能仅因属于这些类别入选。进入候选前，逐项补齐：

1. 公开的实际 Agent 数、并发、任务持续时间、协调事件次数及其时间分布；消息大小或可核查的大小估计，以及合理的扇出。
2. 按本页服务器配置和所需 Worker 槽位，计算共享 Leader 处的事件/秒、单方向正文及 80% CPU 水位对应的每事件 CPU 时间；列出所需 Worker 服务器数、Leader 数和模型服务容量。
3. 根据公开数据或实测估计 Leader 的可持续处理能力，检查 Worker、模型、存储及构建测试仍有余量；同时考虑真实连接、网络包、峰值、重试和链路共享。
4. 在相同真实工作量下比较增加 Leader CPU、链路带宽及卸载处理后的吞吐、尾延迟和丢包。先验证可靠性和一致性，再判断是带宽、包处理、软件协调，还是其他瓶颈。

只有找到有足够依据的具体应用后才补入候选。压力重放用于测可承受上限；不得把人为配置的高事件率写成项目原生负载。
