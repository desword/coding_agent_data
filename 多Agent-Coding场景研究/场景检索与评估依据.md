# 多 Agent Coding 场景：检索与评估依据

本文用于后续寻找公开案例，研究在多 Agent 软件开发中，能否将协调者的一部分消息分发、依赖跟踪与结果协调卸载到可编程交换机。目标包括**网络带宽瓶颈**和**服务器消息、包或协调状态处理瓶颈**；不要求两者同时出现。是否存在瓶颈，以及瓶颈在哪里，必须通过测量和对照实验确定。

## 一、必须具备的场景特征

1. **真实的多 Coding Agent 开发**：公开资料说明多个真实 Coding Agent 参与编码、测试、审查、修复或集成。可以使用 Codex、Claude Code 等主流工具，也可以是其他有实际使用依据的 Coding Agent。接受开源项目、公司公开实践和论文系统，不强制提供完整代码或测试轨迹。
2. **协调者与多个 Worker**：存在 Leader Agent、软件 Orchestrator 或两者组合，负责部分任务分解、启动、结果收集、失败反馈、任务重新分配或集成协调。协调者不必每次都调用模型。
3. **存在相关联的开发任务**：至少部分 Worker 的工作有实际依赖或反馈，例如接口修改影响多个模块、补丁需要由其他 Worker 测试和审查、失败结果触发修复，或者多个子任务完成后才能集成。多个完全独立的 Agent 并发不足以单独证明多 Agent 间的依赖和分发需求。
4. **协调事件可识别、可测量，并有可论证的通信压力潜力**：能从公开资料、代码、日志、工具调用、API 或后续加装的观测点识别任务分派、变更通知、失败反馈、结果汇聚、后继触发等事件。候选案例应至少具备下节所列的一条通信压力路径，且能给出公开证据或可核查的推导。仅能识别偶发的少量事件、没有可论证的通信或并发潜力，不作为优先案例。实际规模和瓶颈仍需测试。
5. **允许研究跨服务器部署**：Worker 可以合理运行在独立进程、容器、虚拟机或云工作空间中；公开案例不必原生跨服务器。公开案例已采用的部署，与实验自行增加的跨服务器部署，必须分别说明。

## 二、通信压力：两条主要路径，允许组合

优先寻找至少满足一条路径、并能够说明形成压力的原因的案例：

| 路径 | 需要寻找的依据 | 示例 | 需要测量的关键量 |
|---|---|---|---|
| **每个工作流通信较多** | 一个工作流内有多轮反馈、较多协调事件、一对多分发，或接收者确实需要较多代码差异、测试输出、诊断内容等 | 公共接口变更通知多个相关 Worker；测试失败后诊断、修复和重测反复进行 | 每个工作流事件数与持续时间、消息大小分布、接收者数量和重试轮次 |
| **单个 Agent 较轻量，可提高并发规模** | Worker 不普遍依赖昂贵的专用设备，多个 Worker 或工作流可以并发；多个工作流的协调事件可能汇聚到共享服务 | 不同任务的多个编码、测试和审查 Worker 并发，由共享协调服务管理 | 同时活跃的 Worker、工作流数、每个工作流事件速率、服务器资源占用和共享协调资源 |

两条路径可以组合：多轮协作的工作流也可同时运行多个实例。高并发潜力不代表实际可达到某个数量：需要考虑测试、构建、模型服务、速率限制、成本和服务器容量。工作流并发与同一工作流内 Worker 并发应分别记录，避免把独立任务误当成有依赖的协作。

**包处理也可以是研究目标。** 即使消息正文只是短文本或对象引用，大量小事件在合适的部署和协议下仍可能对接收、路由、复制、依赖状态更新和连接处理形成压力；它们未必导致带宽饱和。逻辑事件数、消息数、实际网络包数、包大小和字节数不是同一个指标，须分别测量。对象存储、Git、模型请求及共享文件系统产生的流量也应分别统计，不能自动算作 Leader–Worker 消息。

**不要预设统一的规模门槛。** 检索阶段记录可验证的并发能力、实测数据或合理依据；不能核实的写“未知”。实验阶段对事件频率、载荷大小、扇出、活跃 Worker 和工作流数量作敏感性分析，测量实际吞吐、资源使用、排队及延迟。仅凭可能扩展到极大规模，并不能证明真实业务已经达到该规模。

## 三、与三项 Leader 功能的匹配

| 功能 | 优先寻找的业务特征 | 可映射的开发活动 |
|---|---|---|
| 消息分发 | 事件需要按任务、模块或类型单播/分发给多个接收者；接收者会变化 | 代码或接口变更通知相关开发、测试、审查 Worker |
| 依赖跟踪和汇合触发 | 后继任务依赖一个或多个前驱；完成状态决定下一步 | 多个模块修改和关键测试完成后触发集成 |
| 结果仲裁 | 汇集多个结果，决定接受、重试或重新分配 | 汇总候选补丁、测试和审查结果，再决定是否集成或返工 |

**Topic 高优先级**：优先寻找公开资料明确使用 Topic 或动态订阅的案例；也接受公开场景表明接收者随任务、模块或影响范围变化，并据此合理设计 Topic 的案例。必须区分“原项目已有 Topic”和“基于真实工作流增加 Topic”。如引用其他案例作为推导依据，应注明来源、共同条件、差异和推导局限，不能把另一案例的实现直接当作本案例事实。

结果仲裁不要求一定有多个并行候选补丁；测试/审查结果汇合后决定集成或返工也可以。交换机可研究结果到齐的状态跟踪、触发与路由；代码语义理解及最终语义仲裁由 Leader、AI Gateway 或其他软件组件承担。

## 四、公开案例证据与实验扩展

每个候选案例分别列出：

1. **公开明确说明**：原文、代码或可信资料直接支持的事实，附具体链接。
2. **合理推导**：由本案例及其他公开案例支持的推导，说明依据、相同前提、不同条件和局限。Topic 或跨服务器部署可以采用这种方式论证。
3. **实验扩展**：我们新增的 Topic 路由、跨服务器部署、观测点、并发实例或其他改变，说明哪些原生行为受影响。
4. **待验证**：例如实际 Agent 通信量、发送频率、动态订阅规模、原生依赖汇合或瓶颈位置；没有数据就标记未知。

项目受欢迎、功能存在或能够启动多个 Worker，均不能单独证明实际跨服务器流量、Topic 机制或生产并发规模。优先公开证据充分、可复现或可合理构造实验的案例。

## 五、实验设计和判断原则

- 同时观察消息分发、依赖满足到触发、结果汇合及最终工作流耗时；不要将模型推理、构建、测试或 Agent 工作时间误当网络延迟。
- 区分正文发送、仅传引用和摘要加按需拉取；只有接收者确实需要的内容才计入合理业务通信。避免为了制造流量而无意义放大消息。
- 区分自然运行轨迹与可控压力/重放实验。扩展并发时注明来源及假设，不把压力测试结果说成已公开的真实生产负载。
- 视可行性对比集中式 Leader 中继、Worker 直接通信、普通软件消息代理和交换机卸载方案；保证任务、接收者和语义处理一致，并注明网络拓扑。交换机复制可能减少部分链路或 Leader 的重复发送，但不同接收者的链路上仍可能产生多个副本。
- 分别调整带宽、服务器处理资源、事件频率、大小与扇出，并记录实际网络包、队列、CPU 和延迟，以区分带宽、包处理、软件消息处理、模型/工具执行等瓶颈。完成率、失败和超时需一起报告。
- 现有 HTTP/TLS、本地进程通信不必天然适合交换机处理；应说明协议适配、端到端可靠性、重复和乱序处理、订阅更新一致性、交换机状态容量，以及卸载前后保留的功能。

## 六、当前优先候选框架

[Agent Orchestrator](https://github.com/OrchestratorInc/agent-orchestrator) 值得优先研究。其[公开 README（固定版本）](https://github.com/OrchestratorInc/agent-orchestrator/blob/ca3f3646c52ff4abe9bdc4036f5c17164f783874/README.md)描述 main agent 规划任务、为各部分启动独立 worktree 中的 Worker，以及 CI 失败和审查反馈返回相应 Worker；列出的支持工具包括 Codex 和 Claude Code，也介绍云端工作空间。其[架构文档（固定版本）](https://github.com/OrchestratorInc/agent-orchestrator/blob/ca3f3646c52ff4abe9bdc4036f5c17164f783874/docs/architecture.md)描述管理多个并行会话的 daemon 和相关事件机制。

这些材料支持“并行 Coding Worker、协调和反馈闭环”作为候选模式；**尚不能据此认定**它原生使用动态 Topic、所有 Agent 消息都经 Leader 中继、存在本文所需的多前驱汇合或结果仲裁，亦不能证明跨服务器部署和高并发下的流量规模。后续需进一步核实具体代码、公开实践和实际运行数据，并寻找其他可支撑所需特征的案例。
