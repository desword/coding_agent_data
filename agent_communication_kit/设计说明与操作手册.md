# Codex 多 Agent 通信实验：采集口径

当前第一个实验入口为 [Now in Android 一键测试.command](../android实验/01-NowInAndroid/一键测试.command)，自动准备固定 Android 应用，无需选择项目。运行说明和报告解读见 [Now in Android 实验](../android实验/01-NowInAndroid/README.md)。以下保留采集原理和研究建议。

## 2. 核心结论和统计口径

实验采集的关键是 **Agent 之间可见的逻辑消息正文**。本版从关联的 Codex 会话 JSONL 中提取：

| 事件 | 提取规则 | 统计解释 |
|---|---|---|
| spawn_agent | 提取工具参数中的 message、prompt 或 text | 创建子 Agent 时可见的任务正文；调用不保证已成功送达 |
| send_message / send_input | 提取工具参数中的 message、prompt 或 text | 可见的追加消息；调用不保证已成功送达 |
| followup_task | 提取工具参数中的 message、prompt 或 text | 分派给已有子 Agent 的后续任务；调用不保证已成功送达 |
| wait_agent / wait / close_agent | 输出中 status 或 statuses 下明确标记 completed 的字符串 | 主 Agent 可见的已返回结果；只覆盖此类可识别结构 |

每条正文按 `len(text.encode('utf-8'))` 计算字节数。多个收件人、继承上下文、协议封装、重试、压缩、网络传输、模型请求和读取项目文件不在该统计中。收件方和正文缺失时标记未知或列为待核对，不猜测内容，也不视为 0 字节成功消息。

**结果属于“可识别记录”，不是完整通信量。** 工具调用可能失败；而不同版本的消息可能没有保存在支持的字段中，或被截断、加密、压缩。子会话终态和通知仅保留在原始文件中，不与 wait 结果重复累加。若记录数为 0，只能说明本次未识别到符合规则的内容。

模型调用流量与 Agent 间消息必须分开。比如 Worker 读取 500 KB 源代码，并不表示它将 500 KB 发给 Leader；本版也不会将该文件读取量加入 Agent 间消息统计。相同内容重复出现在不同真实调用中仍按多次记录，镜像通知和子会话终态不重复计入。

## 3. 实验结构

```text
Git 工作区（本地副本）
  └─ Codex CLI
      ├─ 主 Agent（分工、协调、集成）
      ├─ 子 Agent A（模块 A）
      ├─ 子 Agent B（模块 B）
      └─ 子 Agent C（测试或审查）

独立输出目录
  ├─ Codex JSON 事件流与标准错误
  ├─ 匹配主会话及其子孙会话的 JSONL 原始文件
  ├─ 消息明细 CSV（可用 Excel 打开）
  ├─ 进程资源 CSV（可用 Excel 打开）
  ├─ 实验信息和待核对项
  └─ 实验统计报告 Word
```

脚本使用当前 `CODEX_HOME`，未设置时使用 `~/.codex`。它根据事件流中的 root thread ID 找到主会话，再依据会话元信息中的 parent thread ID 递归关联子会话；找不到 root 时不会凭时间把其他会话合并进来。默认不会复制其他账号的全部会话记录，不复制登录凭据。

**已知实现范围：** 脚本以本次 session 文件为主要提取源；事件流用于定位主会话和保留原始证据，并不在本版中二次合并到统计。某些版本的 `codex exec --json` 曾出现子 Agent 创建事件缺失，因此不能只看事件流判断没有子 Agent。不同版本会话结构变化时，应根据原始记录调整解析器。


可配对的发送与接收诊断事件可用于估算包含本地调度的投递耗时；不保证所有 Codex 版本都会输出。工具调用耗时可能包含模型推理、排队与工作任务，不可直接归因于网络通信。

## 8. 资源观测方法

脚本约每 2 秒采集 Codex 进程及当时可见的子进程：进程 ID、父进程 ID、CPU%、RSS 和命令名。RSS 是该进程驻留内存的近似值；采样可能错过短生命周期进程。各进程 RSS 简单相加可能重复计算共享内存，CPU% 的含义随操作系统与多核情况变化。

**不要将进程数等同于 Agent 数。** 多个 Agent 可能处于同一进程；也可能看到由 Agent 启动的测试、编译或 shell 进程。Codex 的会话日志不保证给出 Agent 与 PID 的映射。Docker Desktop 的 VM、容器内进程和远端模型资源也不一定体现在该采样里。

若后续研究明确需要每个 Agent 的独立 CPU/内存，应先确认框架是否原生提供 Agent–PID 或 Agent–container 对应；若没有，就需要额外埋点或有意识地把 Agent 隔离到不同容器。后者会改变部署方式，应与原生运行结果分别标注。


## 10. 下一阶段和实验记录建议

单次跑通后，固定 Git commit、Codex 版本、模型及提示词，重复多次，并记录代码修改量、测试通过情况、总耗时、可识别消息数和消息正文大小。把原始日志抽查结果、未识别字段、失败轮次一起保留。比较任务规模时尽量控制项目版本和提示词。

验证消息完整性后，可扩展：按阶段和语义人工分类；适配其他 Codex 版本；增加多次实验汇总；增加 OpenCode 或 OpenHands 对照；在可控云服务器或多主机上测试网络延迟和通信协议开销。上述扩展尚未包含在本版一键工具中。
