# Codex 多智能体通信实验设计与操作手册

版本：v1.0；适用环境：macOS、本地 Git 工作区、已能正常使用的 Codex CLI。

## 1. 实验目标

使用真实的 Codex 主 Agent 和子 Agent，在现有 Git 项目上开展开发或分析任务，回答：

1. Leader 给各 Worker 分配了什么任务，消息正文有多大？
2. Worker 返回了什么结果，返回内容有多大？
3. 是否出现接口协调、测试报错、修复分派和再次汇报？
4. 能否观察 Agent 对应的独立进程或容器，运行过程占用多少资源？

优先在 Mac 本地运行 Agent 框架，模型可由现有配置提供。先跑通消息采集，再做真实开发和多机对比。Git 项目既可以是你自己的项目，也可以是公开仓库的本地副本。

## 2. 核心结论和统计口径

实验采集的关键是 **Agent 之间可见的逻辑消息正文**。本版从关联的 Codex 会话 JSONL 中提取：

| 事件 | 提取规则 | 统计解释 |
|---|---|---|
| spawn_agent | 提取工具参数中的 message、prompt 或 text | 创建子 Agent 时可见的任务正文；调用不保证已成功送达 |
| send_message / send_input | 提取工具参数中的 message、prompt 或 text | 可见的追加消息；调用不保证已成功送达 |
| followup_task | 提取工具参数中的 message、prompt 或 text | 分派给已有子 Agent 的后续任务；调用不保证已成功送达 |
| wait_agent / wait / close_agent | 输出中 status 或 statuses 下明确标记 completed 的字符串 | 主 Agent 可见的已返回结果；只覆盖此类可识别结构 |

每条正文按 `len(text.encode('utf-8'))` 计算字节数。多个收件人、继承上下文、协议封装、重试、压缩、网络传输、模型请求和读取项目文件不在该统计中。收件方和正文缺失时标记未知或列为待核对，不猜测内容，也不视为 0 字节成功消息。

**结果属于“可识别记录”，不是完整通信量。** 工具调用可能失败；而不同版本的消息可能没有保存在支持的字段中，或被截断、加密、压缩。子会话终态和通知仅保留在原始文件中，不与 wait 结果重复累加。若记录数为 0，只能说明本次未识别到符合规则的内容。

模型调用流量与 Agent 间消息必须分开。比如 Worker 读取 500 KB 源代码，并不表示它将 500 KB 发给 Leader；本版也不会将该文件读取量加入 Agent 间消息统计。相同内容重复出现在不同真实调用中仍按多次记录，镜像通知和子会话终态不重复计入。

## 3. 实验结构

```text
Git 工作区（本地副本）
  └─ Codex CLI
      ├─ 主 Agent（分工、协调、集成）
      ├─ 子 Agent A（模块 A）
      ├─ 子 Agent B（模块 B）
      └─ 子 Agent C（测试或审查）

独立输出目录
  ├─ Codex JSON 事件流与标准错误
  ├─ 匹配主会话及其子孙会话的 JSONL 原始文件
  ├─ 消息明细 CSV（可用 Excel 打开）
  ├─ 进程资源 CSV（可用 Excel 打开）
  ├─ 实验信息和待核对项
  └─ 实验统计报告 Word
```

脚本使用当前 `CODEX_HOME`，未设置时使用 `~/.codex`。它根据事件流中的 root thread ID 找到主会话，再依据会话元信息中的 parent thread ID 递归关联子会话；找不到 root 时不会凭时间把其他会话合并进来。默认不会复制其他账号的全部会话记录，不复制登录凭据。

**已知实现范围：** 脚本以本次 session 文件为主要提取源；事件流用于定位主会话和保留原始证据，并不在本版中二次合并到统计。某些版本的 `codex exec --json` 曾出现子 Agent 创建事件缺失，因此不能只看事件流判断没有子 Agent。不同版本会话结构变化时，应根据原始记录调整解析器。

## 4. 安装前准备

### 4.1 需要的软件

- macOS 和终端；Git。
- Python 3.9 或以上，并可使用 `venv` 和 `pip`。
- 已安装、已登录且账户具有相应使用权限的 Codex CLI。
- 首次运行时需要能安装 `python-docx`，用于生成 Word 报告。

查看软件版本：

```bash
git --version
python3 --version
codex --version
```

如果 Codex 尚未安装，可按官方说明安装。使用 npm 的一种方式：

```bash
npm install -g @openai/codex
codex --version
codex login
```

若已有 Codex 登录状态，通常直接复用现有状态即可；本工具不创建 API Key、不保存密钥。模型调用需要网络；具体登录方式、模型可用性、额度及费用以你的账户与配置为准。脚本不自行安装 Codex。

检查当前版本的多 Agent 功能状态：

```bash
codex features list | grep multi_agent
```

如果输出中有 `multi_agent` 且其状态为 `false`，可以执行 `codex features enable multi_agent` 后再检查。不同版本支持的功能名称可能不同；若命令不支持或不存在该字段，先更新 Codex 并查看该版本帮助。多 Agent 是否实际启动，以本次运行记录为准。

### 4.2 准备 Git 项目

推荐使用单独副本，尤其在执行写入模式时：

```bash
git clone https://github.com/fastapi/full-stack-fastapi-template.git ~/agent-test-project
cd ~/agent-test-project
git status --short
```

这是一个包含前端、后端和测试的真实开源模板。第一轮只读分析不要求将整个项目部署起来；第二轮真实开发和端到端测试可能需要 Docker、数据库及项目自己的依赖，按照该项目的 README 安装。记录实际 clone 的 commit，脚本会将当前 HEAD 写入实验信息。

如果已有项目，直接 `cd` 到自己的 Git 工作区即可。

### 4.3 解压实验工具包

下载 `Codex多智能体通信实验工具包.zip` 后，在终端解压。例如文件在下载目录：

```bash
mkdir -p ~/agent-communication-test
unzip ~/Downloads/Codex多智能体通信实验工具包.zip -d ~/agent-communication-test
```

以下假设解压后存在：

```text
~/agent-communication-test/agent_communication_kit/run_test.sh
```

也可以把 `agent_communication_kit` 整个目录复制进目标项目。脚本自身不自动执行 `git add`、`commit` 或 `push`。工具目录内首次运行会产生 `.venv`，如将工具放入项目，应将 `agent_communication_kit/.venv/` 排除在 Git 之外。

## 5. 一键测试：先做只读验证

进入要测试的 Git 工作区：

```bash
cd ~/agent-test-project
```

运行：

```bash
bash ~/agent-communication-test/agent_communication_kit/run_test.sh --project "$PWD"
```

第一次运行会自动创建工具专用 Python 环境并安装 `python-docx`；以后可复用。默认提示词让 3 个子 Agent 只读分析项目，默认最长 1800 秒。启动后会打印本次输出目录，结束后自动生成报告。Codex 标准输出和错误分别保存在结果目录中，终端不会实时展示完整过程。

如果工具已放在项目根目录，也可以执行：

```bash
bash ./agent_communication_kit/run_test.sh --project "$PWD"
```

### 5.1 结果在哪里

默认输出位置为：

```text
~/codex-agent-experiments/时间戳/
```

每次运行创建新的目录，不覆盖先前数据：

| 文件 | 内容 |
|---|---|
| `实验统计报告.docx` | 会话数、识别消息数和字节数、事件分类、消息摘录及口径说明 |
| `消息明细.csv` | 每条可识别消息的时间、发送方、接收方、内容、大小、状态、来源和行号 |
| `进程资源.csv` | Codex 进程及采样时可见子进程的 CPU、RSS 等采样 |
| `实验信息.json` | 项目路径、Git HEAD、Codex 版本、开始结束时间、root ID 和退出状态 |
| `codex-events.jsonl` | Codex 公开 JSON 事件流原文 |
| `codex-stderr.log` | 标准错误，出错优先查看 |
| `sessions/*.jsonl` | 根会话和可关联的子会话原始记录 |
| `待核对.txt` | 已识别为协作工具调用、但没有提取到明文消息的记录 |
| `使用的任务.txt` | 本次实际使用的提示词 |

CSV 使用 UTF-8 BOM，Excel 可直接打开。表中以 `=`、`+`、`-`、`@` 开头的文本会添加单引号，避免 Excel 将其当成公式；**字节数仍按原始消息计算**。

默认输出目录在项目之外，避免让 Agent 把正在生成的实验日志误读成项目内容。运行记录可能包含代码、提示词和项目细节，分享前自行检查。

### 5.2 跑通的判断标准

打开 Word 和 CSV，同时抽查 `sessions`：

1. `实验信息.json` 中应有非空的 root thread ID，Word 中会话数至少大于 1。
2. 查看 `消息明细.csv` 是否出现 `spawn_agent` 和对应任务正文。
3. 查看是否有明确 `已返回结果` 事件，内容和原始 JSONL 中的 completed 字段一致。
4. 抽查 2～3 条消息的来源文件和行号，核对正文、发送方、字节数。
5. 检查每个子 Agent 是否真的开展了工作，而非仅创建后空回复。
6. 查看 `codex-stderr.log`；退出非 0、超时、会话缺失都需要先排查。

用户提示 3 个 Worker 不意味着实际一定启动 3 个。报告中的会话数量和消息记录才是当前可见证据。若能找到子 Agent 的最终答案，但主会话没有支持格式的 completed 返回，它会保留在原始会话中，**本版不会将其自动算进已返回结果**。

## 6. 第二阶段：真实开发和高通信步骤

确保目标是可修改的项目副本，建议先创建实验分支并确认工作区状态：

```bash
cd ~/agent-test-project
git status --short
git switch -c experiment/agent-communication
```

运行真实开发提示词：

```bash
bash ~/agent-communication-test/agent_communication_kit/run_test.sh \
  --project "$PWD" \
  --mode write \
  --prompt ~/agent-communication-test/agent_communication_kit/prompts/development.txt \
  --timeout 3600
```

此模式使用 `workspace-write`，允许 Codex 在目标工作区内执行修改。最终是否能运行项目的安装、容器、网络或测试命令，取决于 Codex 的沙箱、权限和本机环境；执行结束后应检查 `git diff`、项目测试和 stderr。脚本不会自动提交或推送更改。

```bash
git status --short
git diff --stat
```

内置开发提示词让主 Agent 按项目实际情况选择小功能、分工、开发、测试和修复。它是通用模板；为让不同轮实验可比，建议复制一份并写入明确功能需求、验收标准和可用测试命令。

特别观察 **接口对齐 → 集成测试 → 失败定位 → 重新分派 → 再次测试**。目前报告按调用工具类型分类，不会自动可靠地给出“需求分配/报错/接口协调/修复”语义标签；研究人员可根据明细、时间戳和内容进行人工标注，再决定是否增加分类脚本。

## 7. 自定义任务与运行参数

创建自己的文本文件，例如 `my-task.txt`，写入实际任务。保持目标、角色、可修改范围、测试和验收条件明确。

```bash
bash ~/agent-communication-test/agent_communication_kit/run_test.sh \
  --project "$PWD" \
  --prompt "$HOME/my-task.txt" \
  --mode readonly \
  --timeout 1800
```

| 参数 | 作用 | 默认值 |
|---|---|---|
| `--project` | Git 工作区路径 | 当前目录 |
| `--prompt` | UTF-8 任务文本 | `prompts/smoke.txt` |
| `--mode` | `readonly` 或 `write` | `readonly` |
| `--timeout` | 整体等待的最长秒数，超时终止本次进程组并保留已有记录 | 1800 |
| `--output` | 指定本次结果目录；目录必须尚不存在 | 自动生成唯一目录 |
| `--analyze` | 对已有结果目录重新生成报告，不再次调用模型 | 不启用 |

重新分析示例：

```bash
bash ~/agent-communication-test/agent_communication_kit/run_test.sh \
  --analyze ~/codex-agent-experiments/某次运行目录
```

修改解析器后可以使用这个命令重复生成报告；会覆盖该次的 Word、CSV、实验信息和待核对文件，但保留原始会话与事件流。需要保留旧报告时，先复制该运行目录。

## 8. 资源观测方法

脚本约每 2 秒采集 Codex 进程及当时可见的子进程：进程 ID、父进程 ID、CPU%、RSS 和命令名。RSS 是该进程驻留内存的近似值；采样可能错过短生命周期进程。各进程 RSS 简单相加可能重复计算共享内存，CPU% 的含义随操作系统与多核情况变化。

**不要将进程数等同于 Agent 数。** 多个 Agent 可能处于同一进程；也可能看到由 Agent 启动的测试、编译或 shell 进程。Codex 的会话日志不保证给出 Agent 与 PID 的映射。Docker Desktop 的 VM、容器内进程和远端模型资源也不一定体现在该采样里。

若后续研究明确需要每个 Agent 的独立 CPU/内存，应先确认框架是否原生提供 Agent–PID 或 Agent–container 对应；若没有，就需要额外埋点或有意识地把 Agent 隔离到不同容器。后者会改变部署方式，应与原生运行结果分别标注。

## 9. 常见问题

**1. 找不到 codex**：先用 `codex --version` 验证安装；重新打开终端检查 PATH。安装完成后单独执行 `codex login`。

**2. 安装报告依赖失败**：检查 Python、pip 和访问 Python 包仓库的网络，再执行 `python3 -m pip --version`；工具不要求项目安装 python-docx。

**3. Word 中消息数为 0**：查看事件流是否包含 `thread.started`、实验信息中的会话数、`待核对.txt` 和 stderr；确认实际有子 Agent。必要时在 `sessions` 手动搜索 `spawn_agent`、`send_message`、`followup_task`、`wait_agent`。不同 Codex 版本的日志形式可能不同。

**4. 退出码不为 0**：报告仍会尽量生成。查看 `codex-stderr.log`，确认账户权限、网络、模型、项目以及沙箱限制。超时时退出码为 124，当前结果可能不完整。

**5. 子 Agent 有结果但统计没有**：本版只统计主会话工具返回中显式 completed 字符串；有些版本采用其他格式。保留原始日志后调整解析器，不要把子会话最终答案和主会话返回直接相加。

**6. 只看到了几个进程**：可能多个 Agent 共享运行时，也可能采样间隔错过了短进程；不能据此断定只启动了几个 Agent。

**7. Windows 或 Linux 能否使用**：脚本使用 Bash、Python 以及类 Unix `ps`；本版设计优先 macOS，Linux 有机会使用但需要验证。Windows 建议后续单独适配 WSL。

## 10. 下一阶段和实验记录建议

单次跑通后，固定 Git commit、Codex 版本、模型及提示词，重复多次，并记录代码修改量、测试通过情况、总耗时、可识别消息数和消息正文大小。把原始日志抽查结果、未识别字段、失败轮次一起保留。比较任务规模时尽量控制项目版本和提示词。

验证消息完整性后，可扩展：按阶段和语义人工分类；适配其他 Codex 版本；增加多次实验汇总；增加 OpenCode 或 OpenHands 对照；在可控云服务器或多主机上测试网络延迟和通信协议开销。上述扩展尚未包含在本版一键工具中。
